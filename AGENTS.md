# MineMuster

Time clock, the equipment checklist, pre shift exams, maintenance requests and payroll hours for a mine crew, for any company that uses it. Expo (React Native) + TypeScript; one codebase for iOS, Android and web. Read `README.md` for what the app does and where the build stands.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. Before writing code that touches an Expo, EAS or React Native API:

1. Read the major version of `expo` in `package.json`.
2. Read the matching versioned docs at `https://docs.expo.dev/versions/v<major>.0.0/`, or the package's own type definitions in `node_modules/<package>/build/*.d.ts` when the network is closed.

## Commands

```bash
npx expo install <package>   # always use instead of npm install for Expo/RN packages (SDK-matched versions)
npm run web                  # dev server in a browser
npm test                     # Jest
npm run typecheck            # tsc --noEmit
npm run build:web            # static export to dist/
npm run build:preview        # the web build packed into one HTML file in preview/
npx eas build --profile production   # the App Store and Google Play builds (eas.json; needs the Expo organization's sign-in)
npx expo-doctor              # dependency and config health
```

- With no network access to Expo's servers, prefix Expo CLI commands with `EXPO_OFFLINE=1`.
- `npm run typecheck` runs `tsc` with a larger stack on purpose. The per-icon type files in `lucide-react-native` recurse deeply enough to overflow Node's default stack; plain `npx tsc --noEmit` crashes with "Maximum call stack size exceeded".
- **The preview file has to stay under 2 MB** (2,097,152 bytes). The Claude phone app has opened every smaller one as a preview and shown every larger one as code. `scripts/build-preview.mjs` packs the fonts as the WOFF2 copies in `scripts/preview-fonts` to keep it there, and warns when the file gets close. When a font package is updated or the app loads another weight, remake the copies with `scripts/compress-preview-fonts.py`; a test holds them to the fonts `App.tsx` loads.
- A build reads `.env.local` when it is exported, and the bundler keeps what it read. After changing a setting there, or setting one on the command line, export with `--clear`.

Run the tests and the typecheck before calling any task done.

## Project conventions

- **Navigation is React Navigation, kept in memory** (`src/navigation/RootNavigator.tsx`), not Expo Router. There is no URL routing, so the web build can run from a single file or inside a frame. Do not add `linking` config or Expo Router without a reason that outweighs that.
- **Rules live in `src/domain/` as pure functions with tests.** Hours, lunch rules, overtime, the GPS boundary, the equipment checklist and its daily card, pre shift exams and standards. Change a rule there and update its test; screens only display results.
- **Hours are hundredths of an hour, as whole numbers** (1225 = 12.25). Convert minutes with `toHundredths` and never add up rounded floats. This matches the crew's paper timesheet method and keeps every screen and export in agreement.
- **Hours rules follow the company's state** (`rulesFor(company.state)` in `src/domain/stateRules.ts`; `useRules()` in screens). Daily overtime, double time, the seventh-day rule and the meal period (when it is owed, whether it has a start-by time, a second meal) are fields of `TimeRules`; a state with none of its own gets `FEDERAL_RULES`. Pass the rules to every hours function a screen or export calls; never write California's numbers into copy (use `overtimeSummary`, `mealSummary`, `flagHelp`, `deadlineWords`). Every state's rules were checked against its statute or agency, and each carries its citation; change one only against the law itself. A rule the app cannot apply goes in the state's `note`, not into made-up numbers. The lunch itself is `LUNCH_MS`, 30 minutes, everywhere.
- **Lunch is one tap and ends by itself.** `startedLunch` in `src/domain/time.ts` writes the end of a lunch when it starts: 30 minutes later. Whether someone is at lunch is always worked out from those two times (`lunchEndAt`, `mealStatus`), never from a timer or a background task, so it is right even if the app was closed. Do not add an end-of-lunch punch. Which notifications are waiting is decided by `reminderPlan` (tested; in a browser tab that another tab takes the records from, `remindersToLetGo`) and only handed to the phone in `src/services/reminders.ts`. Once a lunch's end has come, `reminderPlan` never takes its notice off the phone while the shift is open (the phone has shown it, or is holding it back and must still show it), whatever runs then: start-up, a punch or the Lunch reminders setting; a clock-out takes it off, since it would only say they are back on the clock after they left. The lunch-over notice goes out as an alarm (`alarm` on the reminder: Android's alarm-clock delivery), which a phone saving battery does not hold back; on Android that needs the person's Alarms & reminders permission (`SCHEDULE_EXACT_ALARM`, never `USE_EXACT_ALARM`), and while it is off the Clock screen asks for it on a shift (`OnTimeNotice`). On Android the lunch-over notice has a channel of its own, apart from the deadline reminders (`src/services/notificationChannels.ts`), so turning those off in the phone's settings never silences it; at lunch the Clock screen says when either notifications or that channel are off (`lunchNoticeState`). The Clock screen reads both of those and Alarms & reminders (`onTimeNotices`) again, without asking, whenever it opens or comes back into view on a shift and whenever the app comes back to the front, not only after a punch, since a person can change them in the phone's settings at any time. Whenever the app comes back to the front on a shift, whatever screen is in front, the reminders still ahead are handed to the phone again (`watchReminders` and `handOverWaiting` in `src/services/reminders.ts`, started in `App.tsx`; in a browser only by the tab that saves the records, since a tab another tab takes them from takes its own off, all but a Lunch is over whose time has come, and a tab that has them again hands them over once it has read them), so one turned on meanwhile from another tab still comes; that hand-over asks nothing and takes nothing off the phone (it hands over only the reminders still ahead), and the Clock screen's own read on coming back is for its warnings only. Every hand-over (at start-up, after a punch, after the Lunch reminders setting or the company's state changes, this one, and a browser tab's as it loses or gets back the records) goes through one queue in `src/services/reminders.ts`, one at a time, each planned from the store when its turn comes, never when it was asked for: a punch's location read can show a system dialog that sends the app to the back and the front again, and the hand-over planned before the punch must never land after it. Nothing else calls `scheduleLocal` or `cancelLocal`. A hand-over the phone has not answered in 10 seconds (`TURN_MS`) no longer holds up the next; it makes no more calls, and once it answers it is made once more from the store as it is then. `scheduleLocal` leaves a reminder due within the second as the phone holds it, since it could no longer be handed over in time. Never reuse the old shared channel's id, `lunch`: Android brings a deleted channel back with the settings it had. The phone is asked for notifications only at clock-in and from the Lunch reminders setting; handing it reminders (`scheduleLocal`) never asks, since Android 13 and later stop asking for good after a second no.
- **Pay periods are the company's own, or none** (`settings.company.pay`, a `PaySchedule`; the rules are in `src/domain/payPeriod.ts`). Every function that finds a period takes the schedule; never assume one. With no schedule there is no pay period anywhere: hours are shown by the workweek and the month (`src/domain/spans.ts`, `useSpans`). A pay date on a day the bank is closed moves the way the schedule says (`ifBankClosed`). Overtime is always figured over whole workweeks and then summed for the days in the range (`computeRange` in `src/domain/payroll.ts`); never compute overtime from a pay period's days alone. Holiday, PTO and sick hours are paid leave: they add to the total and never count toward overtime.
- **The paper forms are the mine's own, and they are data.** The Operator Equipment Checklist is one card for every machine: 21 lines in `src/domain/templates.ts`, in the order and wording they are printed. Do not add, drop, reorder or reword a line; `checklistFor` only picks the standard shown beside a line for the type of machine. The Pre Shift Exam's three columns and 20 conditions are in `src/domain/areaExam.ts`, also as printed. Tests hold both lists to the paper. The legend at the foot of the card (`ANSWER_LEGEND`) is word for word as well, capitals and punctuation included: do not tidy it.
- **Shifts are day, swing and night** (`SHIFTS` in `src/domain/areaExam.ts`), and a pre shift exam is for one of them. `startingShift` picks the shift a form starts on from the time the person clocked in; the hours it goes by are in `shiftAt`, and they are a guess until the mine gives its own. Use them for that starting choice and nothing else: do not work out from them that an exam is due, done or late. Name a shift with `shiftLabel`.
- **Use the paper's words.** "Equipment checklist" (not "pre-op"), "pre shift exam", "maintenance request", "Bad Order", "red tag", "equipment hours".
- **Standards are cited only once checked.** A line cites MSHA with `cfr` and OSHA with `osha`, or a list of `refs`; every key must exist in `STANDARDS` in `src/domain/standards.ts` (tests enforce it). Do not cite a regulation you have not verified against the regulation text. A line with no checked standard carries none.
- **Time tracking is a switch** (`timeClock: false` on the company; `keepsTime`). With it off the app is the safety forms alone: no Clock or My hours tab, no payroll, corrections, boundary, lunch reminders, decimal chart or hourly rate, and it opens on the checklists. Anything new about time or pay checks `keepsTime` before it shows; nothing about safety does.
- **The payroll hours file** (`payrollCsv` in `src/domain/payrollCsv.ts`, `payrollHoursFile` in `src/services/reports.ts`) is made from the same `computePayroll` as the Excel export, with each person's `payrollId` and the company's `payCodes`. It holds hours only: never a rate or an amount. No vendor's layout is built in, because none could be checked against the vendor's own text; add one only from that vendor's import template, with a test.
- **The PDF for an MSHA inspector** (`inspectorReport` in `src/services/inspectorReport.ts`) is made from the same records as the Excel safety log, so the two agree, and each section names the standard it answers to. It is written by `src/services/pdf.ts` in the standard Helvetica fonts (no font is packed into the app), so its text is Windows-1252: a character outside it, like a minus sign or an emoji, prints as "?". The font widths in `pdfMetrics.ts` are made by `scripts/make-pdf-metrics.py`; do not edit them by hand.
- **A sheet has three columns or one.** Most area sheets check each line for guarding, electrical and safe access. Some mark each line OK or BO once: `single` on the sheet, set by the "One OK/BO column" switch or by `[OK/BO]` after the area's name in a build setting. An exam made on one says so (`single` on the exam) and holds the one answer in all three cells, so `rowAnswer` reads it like any other. Wherever the three columns would be asked for, named or printed, a one-column exam has none: the form, `ExamSheet`, `examFindings` (its `where` is `ON_THE_SHEET`), the problem text of a maintenance request and the Exam Lines sheet of the export.
- **Area sheets are records in the store** (`areaSheets`), changed by a supervisor in the app. A build can name its own in `EXPO_PUBLIC_AREA_SHEETS`; `parseAreaSheets` reads them and `withSheets` adds them at start-up, until the phone is first connected to a company. The repository only holds the made-up `SAMPLE_AREA_SHEETS`, a plant nothing like the mine's. Do not model a sample, a test string or an example on a real sheet, not even by its generic line names; a test compares the samples with `.env.local` wherever that file names sheets.
- **A signed record is not rewritten.** A checklist keeps its answers and an exam keeps the lines and labels it was made on, whatever happens to the sheet afterwards. The date a condition was fixed is added to its exam (`withFix`; the first date stands), and so is the request it was sent on (`withMrf`).
- **What is signed is what the person can see.** A note, a danger mark or an unsafe mark goes on the record only with a Bad Order. One typed and then withdrawn, by changing the line back to OK or N/A, is dropped by the rules (`examRow`, `signedAnswers`), not just hidden by the form. A form is signed once: the store hands back the record already made when the same draft arrives twice, and each form's button runs once.
- **Everything works with no signal.** A record is saved on the phone when it is signed; nothing waits on a network, and no screen may need one to finish a punch, a checklist, an exam or a request. `changesToSend` in `src/domain/sync.ts` works out what the company's server does not have, by a version hash of each record, and `src/services/sync.ts` sends it in batches when there is signal (`expo-network`), trying again with a longer wait each time. Each change carries the version the server last had (`base`), and a record taken off the phone goes as a deletion (paid leave a supervisor took off, a unit taken out of the fleet, the oldest turned-down punches past the last 200); a record that a deletion from the company took off is not sent back. The hourly rate, the accounts and passwords and this phone's own settings never leave the phone, nor does any record that names a sample person anywhere in it, nor the sample company or site; a preview build, and a build that starts with the sample crew, sends nothing at all (`CAN_SEND` in `src/config.ts`). A new kind of record gets its place in `changesToSend`, ahead of anything that points at it, with a test; the one exception is the `mrfId` back-pointer on an inspection or an exam line, which the server takes as a soft link. Records people make get their ids from `uid`, random enough that two phones never make the same one; an area sheet's id is a slug of its name, so the server matches sheets by company and slug. A send with no answer in 30 seconds counts as failed, and its request is aborted. Every request supabase-js makes has a time limit too (`timedFetch` in `src/services/server.ts`, since Android's fetch has none): 30 seconds to the last of the answer, and a little more than delete-account's own minute for an edge function, so that one is what ends it; a request given up is put in the same words as no signal. A round sends only while the phone still sends through the same transport to the same company (`still` in `sendWaiting`): a disconnect stops it at once, and an answer that comes back after it is not noted (`markSynced` takes the company that answered). A change the server cannot take (`SERVER_LIMITS`), or one a call was turned down for (`refused`), is held back and shown, and the rest still go. A failed send or read says why (`SendTrouble`: no signal, signed out, off the roster, what the server said, and, from the read only, MineMuster stopped for the company), and the records rows say that, not only "could not be reached". With no company connected, no transport is set (`setSyncTransport`), and the app says the records stay on the phone. A phone connected to its company also receives the company's settings, roster, fleet and area sheets (`REFERENCE_KINDS`) through `read_shared_records`, a page at a time by `seq` after a cursor that is saved in the same write as the records it covers; a page read for another company, account or epoch is not applied (`applyReceived`). Each round first sends what was made on the phone, then reads the sign-in's own row of the roster, then the four kinds, then sends the phone's changes of those four, made from what it just read. A round runs at start-up, on connecting, when signal returns, when the app comes to the front, a few seconds after a record changes on the phone, every five minutes while the app is in front, and from Send and receive now on Company account; there is no background task. `mergeRows` in `src/domain/receive.ts` (tested) merges each page: a person always takes the company's version; what the phone has not changed takes the company's; a sheet or the settings changed both here and elsewhere takes the company's and says so; a unit changed both here and elsewhere, or one the phone never sent or received, takes the company's with its status merged (`mergeStatus`: three ways, or the worse of the two with no base) and the higher reading; a unit that comes is never kept better than this phone's own open requests on it. A row this version cannot read (`readRecord`) is passed over, not sent, and read again at the next start of the app. On a connected phone `sortedChanges` never sends a person; from a sign-in that is not a supervisor's it sends no sheet, no settings and no new or removed unit; it sends nothing of the four kinds the server never had until the phone has read the company's to an empty page, and no settings whose company fails `checkCompany`. A change the server turns down for the phone's sign-in (`supervisor_only`, `not_yours`, `signed`), or a record of the four kinds it will not take as it is, is held (`receiving.held`) and listed on More, not counted as sent, and goes again only once the record changes or the sign-in is made a supervisor's. Of the four kinds, a change answered `superseded`, `copy` or `deleted` makes the round read and send again, at most twice, and `open_request` puts the unit back at least at the company's floor (`keepFloor`). Every other kind (time, leave, checklists, equipment use, exams and requests) is not received.
- **The company server is a build setting** (`SERVER` in `src/config.ts`, from `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_KEY` in `.env.local`). With either empty, or in a preview build, nothing about a server is in the build: `src/services/connection.ts` loads `src/services/server.ts` (and supabase-js with it) only behind a condition written with the two settings and `EXPO_PUBLIC_DEMO === '0'` themselves, which the bundler folds to a constant, and `RootNavigator` loads the company sign-in screen and the Company account screen the same way. A build that connects needs `EXPO_PUBLIC_DEMO=0` and no sample crew (`CAN_SEND`): a preview's controls make punches up (simulated GPS, moving a clock-in back, opening as the owner with no account), so a preview never sends. `parseServer` refuses a secret key. Reach the server only through `server` and `CAN_CONNECT` from `connection.ts`; never import `services/server.ts`, `domain/serverAnswers.ts` or `@supabase/supabase-js` from code that every build has, or the public preview grows by them. `CAN_CONNECT` is false in a preview and in a build that holds the sample crew. What the person typed and what the server answered are read and put into words in `src/domain/serverAnswers.ts` (tested); the connection itself is `connectedCompany` in the store, with the server account that joined it (`userId`), and `watchConnection` hands the company's transport (`companyTransport`, which sends and reads) to `setSyncTransport` from start-up on, only while that account is signed in. Who the phone's company sign-in is to the company is `receiving.role` and `receiving.name`, which each round's standing read sets (`standingChange`); a connected phone's powers, what it sends and whose account it may hold go by them (`supervisorHere`, `sortedChanges`, `accountHere`). Another account signed in is checked against the company's roster (`my_companies`) before anything is sent as it; signed out, the phone holds its records and says to sign in again (`useServerAccount`). The server account belongs to the phone, and in a build with a server the app's own Sign out ends it too, once everything on the phone has reached the company (see Signing out of a phone below). A build with a server offers no Apple, Google or Microsoft sign-in, which only ask for a typed name: its way in is the company sign-in, a typed name that the server checks against a passcode, or email for supervisors (the next bullets). A supervisor-only action checks the role in the store, not only on the screen. A phone sends to one company (`connectProblem`, `syncedWith`): records that went to one never go to another until the device is cleared, which in a build that keeps real records only a supervisor may do (`clearDevice`), or the person whose own sign-in it sends with, by signing out of the phone or deleting their account, each once nothing on it would be lost (`forgetPhone`, `deleteMyAccount`). Signing out of the server (`signOut` in `src/services/server.ts`, which `disconnect` and `signOutOfPhone` call) signs out this phone only (`scope: 'local'`), and takes the session off the phone even when supabase-js keeps it for want of signal or the server has not answered the sign-out in 10 seconds (`SIGN_OUT_WAIT_MS`); the client it lets go can then put nothing back on the phone. supabase-js adds about 0.3 MB, so a build that names a server packs to more than the 2 MB preview limit; the public preview names none. Since `20261120000100` the server checks every record of the settings, the roster, the fleet and the area sheets sent to it, from anyone, against the shape the phones read (`shared_record_problem`, the server's side of `readRecord`), but of a company only the name and the state: its pay schedule, mine ID and earning codes are checked by the phones and by the dashboard's own save. It also writes a change to one it already has only on top of the version the change was made from, never writes a unit's status better than the company's open maintenance requests on it, and gives an account that is not a supervisor's the roster without payroll IDs (`supabase/README.md`).
- **Crew sign in with the company code, their name and a passcode, and have no email** (migrations `20261122000100` and `20261122000200`, `supabase/README.md`). A crew account is an ordinary Supabase Auth user that the server makes, never the person: a hidden address `crew-<32 hex>@crew.minemuster.com` that receives no mail and that nothing is decided from, and a long password the database works out from it with a key of its own (`crew_login_password`). A crew account is one with a `crew_logins` row. Nobody, the person included, ever sees the address or the password, and the app is never handed the address: `accountOf` in `src/services/server.ts` is the one point of entry for an account, and gives a passcode account none. The passcode is 6 to 12 digits and not an easy one (`passcodeProblem` in `src/domain/passcode.ts` and `crew_passcode_problem` are one rule, and a test holds them together); it is kept only as a salted digest made with a key the database made for itself, in tables no API role can read. 5 wrong in a row lock the account for 15 minutes and 10 lock it until a reset; the right passcode is refused while it is locked, and every wrong try is counted in the database, one at a time. A reset code is 6 digits, good for 30 minutes and 5 tries, made by a supervisor on the dashboard and kept only as a digest; it works while the account is locked, and using it sets the new passcode, clears the lock and signs the account out everywhere else (`crew-auth` does it, or the phone when that failed: `signOutOtherSessions`). Two edge functions, both deployed with JWT verification off: `crew-auth` for the app (`lookup`, `sign_up`, `sign_in`, `reset`, `confirm`) and `supervisor-tools` for the dashboard (`invite`, `resend`, `delete_crew_sign_in`). `crew-auth` turns down any request with a browser `Origin`, so passcode sign-in is on iOS and Android only and the web build offers email. Each of its requests but `confirm` is counted against the caller's network address, `cf-connecting-ip` first, else the first `X-Forwarded-For` entry, at most 30 in 10 minutes (`crew_try_counted`, which keeps only a keyed digest of the address); lookups by a signed-in account (`company_by_code`) are not limited, and anon can no longer call it. A passcode account never holds a supervisor's row (supervisors sign in with email) and holds rows in one company only: the roster's write trigger and `crew_keep_passcode` refuse each the other way round (`supervisor_needs_email`, `passcode_account_elsewhere`). Known limits, accepted: anyone with the company code can sign up under a name not yet signed up, so a supervisor sees who has joined on the Roster page and fixes a wrong one with Delete sign-in, and rotating the code stops people who have left; 10 wrong tries lock a name until a reset, about 10 in a million per account with easy passcodes refused, and there is no company-wide slowdown, on purpose, since one person could then lock the whole crew out; names written the same always answer ambiguous at sign-in; a removed crew account blocks a sign-up under its exact name until a supervisor deletes that sign-in or adds a row for the newcomer; records a deleted account sent stay with the company, and a new sign-in for the same person cannot change a shift the old account opened, so a supervisor closes it with a correction.
- **One person per phone, signed in until they sign out.** The first screen of a build that connects is the company sign-in (`CompanySignInScreen`): the company code, then Sign up (first and last name, a passcode typed twice) or Sign in (name and passcode), and, under Supervisor? Sign in with email, email and password (supervisors, and any account that already signs in with email). The phone keeps the session, finds the person's company (`my_companies`) and connects to it, and once a round has read the company's records to the end (`receiving.caughtUpAt`) the store opens the person's own account by itself (`openOwnAccount`): no second account and no second password. Only the person the phone's company sign-in is for has an account on it (`ownPersonHere`, `signInPerson`; `accountHere` turns every other away, whatever the sign-in's role). A build that connects has no local email-and-password account; a preview and a build with the sample crew keep theirs (`AuthScreen`). **The app never signs anyone out by itself**: not for time, for no signal, for an update, for a restart or for an expired access token, which supabase-js refreshes once there is signal. A session ends only when the person signs out of the phone or deletes their account, a supervisor deletes the sign-in, or a passcode reset signs the account's other sessions out; a person taken off the roster stays signed in, to delete their account and to end use of a unit.
- **Signing out of a phone empties it, so it waits until nothing on it would be lost** (`signOutOfPhone` in `src/services/connection.ts`, `forgetPhone` in the store, and the pure `signOutBlockers` in `src/domain/accountDeletion.ts`). In a build with a server, More's Sign out and Company account's ask first (the company sign-in screen's Sign out of this phone does not), then sign out of the server too and empty the phone the way `clearDevice` does, to start as the build does. Only the phone's own person may. It is refused, each thing that holds it up saying what to do, while the person is on the clock, at lunch or has a unit checked out; anyone else has an account on the phone; the company's records have not been read to the end; anything is waiting, stuck or held (turned down by the company); or the company sign-in is signed out on the phone. A sign-in off the company's roster cannot send, so what it made holds signing out until it is put back on the roster or the person deletes their account. The shared signing-out state (`signingOutWhile`) holds the company sign-in screen until the server's sign-out is done, so it does not find the company again and reconnect the phone meanwhile. Signing back in needs signal. With nobody's account open, a person taken off the roster can still sign out from the sign-in screen's card, which closes any account left open, lets go of the company and signs out of the server without emptying the phone, and can end use of a unit there. Company account (More) is the connected view only: the company, records and what is sent and received, Send and receive now, Sign out of this phone, Delete my account, and Sign in again for a company sign-in signed out of the server. Its own sign-in and join forms are gone: a phone joins its company from the company sign-in screen.
- **The store builds are made by EAS from `eas.json`**: `production` for the App Store and Google Play, `internal` for trying a build on phones. Both connect (`EXPO_PUBLIC_DEMO=0`, and `EXPO_PUBLIC_SAMPLE_CREW=0`, not empty: with no roster an empty value means the sample crew, and a build with them never connects), with every private setting blank (a single space: EAS refuses an empty value, and the app reads a blank one as none), `.env.local` not read (`EXPO_NO_DOTENV=1`), and the customer's traced logo left out (`EXPO_PUBLIC_LOGO_ART=0`). The company server's address and key are set in the EAS environment (production and preview), never in the repository. `app.json` names the Expo organization and project the builds are made in (`owner`, `extra.eas.projectId`), and builds and credentials are kept by that project. `scripts/__tests__/storeBuild.test.ts` holds `eas.json` and the store settings in `app.json` to that: iPhone only, no export-controlled encryption, no Android cloud backup of what never leaves the phone, location while in use only with a purpose text that says supervisors see it (`LOCATION_PURPOSE` in `src/config.ts`; Android's own prompt has no room for it, so on Android the app shows it first, the one time the phone is about to ask: `useLocationPurpose`), and local notifications only. Never name a profile "preview": here that is the demo build that never sends.
- **The privacy policy and the help page open from the app** (`WEB_PAGES` in `src/config.ts`, `WebPageLinks`): on the sign-in screen, before anyone has an account, on More and on Company account. The stores require the privacy policy inside the app; keep the links in every build.
- **State is one Zustand store** (`src/store/useStore.ts`) saved to device storage (`recordStorage` in `src/services/storage.native.ts`; the web keeps `storage.ts`). On Android the records are files of their own, because Android cannot read back an AsyncStorage row over about 2 MB. expo-file-system has no way to make a write reach the disk first (no fsync), so a power cut can tear what was written in the last half a minute or so, and a punch saves several times within seconds: each save writes the records once, whole, as `<key>.json.part`, and renames it to a copy of its own, `<key>.cp-<place>-<b|a><steady>-s<start>.json`, whose name says its place (from the phone's clock, past every copy and every mark), when it was written by the steady clock (`performance.now`; `b` when that clock read 10 s or more as the start first read the records, so counts from the phone's start, `a` otherwise) and which start of the app wrote it (the steady time that start first read or saved the records at). The rules count, on purpose, on React Native reading `performance.now` from `std::chrono::steady_clock`, which on Android counts from the phone's start and stops while it sleeps (`NativePerformance::now` in React Native 0.88, whose own comment says that "should be carefully changed eventually"). Without it the copies could not be kept to a few after starts of the phone close together (34 were measured), and under a clock that counted from the app's start a power cut could leave nothing whole to read (Records not read). `src/services/__tests__/steadyClock.test.ts` reads the installed React Native's source and fails once it no longer reads that clock, so an upgrade that made it count from the app's start is caught before it ships, and the rules are looked at again. A rename never writes over a file, and older copies go only by the rules in `src/services/recordCopies.ts` (pure and tested, with both clocks passed in), at a save, once the store has read the records at a start (`opened`, through `recordsRead`), or on a timer with the app idle. Settled is judged by the steady clock alone, never by the phone's clock or a file's modificationTime, which a clock set right by the network or by hand can make jump: a copy is settled once the steady time in its name is two minutes or more below now, or this session has held it two minutes, or both clocks count from the phone's start and its time is above now (written before the phone last started, which put it on the disk; it is then renamed `-e<steady>` so that a later start still knows). The steady clock stops while the phone sleeps, which only makes settling slower. The newest settled copy this session knows whole is the anchor (one it has not read is read once, and goes if torn), and every copy older than it goes. Of the newer ones, while no more than five are kept in all (`MOST_COPIES`, the anchor among them), these are kept in this order: the newest, the copy before the latest sleep (the phone's clock running 30 s or more ahead of the steady one between two copies), at a save the copy it replaced when the phone's clock says it was written a minute or more ago, the newest of each minute of steady time, newest first, and then, newest first, the last copy of each start of the app before the next (the phone may have started between them, which the steady clock does not show once the next start reads it past that copy's time) and the copy before each earlier pair the phone may have slept between (a jump of the phone's clock forward looks like a sleep), and last, newest first, the copy before each nap (the phone's clock running 5 s to 30 s ahead of the steady one between two copies, `NAP_MS`), which the phone put on the disk as it napped. Besides, every one whose steady time cannot be set beside this start's is kept until it settles, whatever the count: under React Native 0.88's clock, only a copy of another boot just as the phone or this start began (when the app first reads the records within 10 s of the phone starting, the copies of the boot before stay beside its own until it has held them two minutes, more than five meanwhile), or one with no steady time from an earlier build. So a whole copy that has had time to reach the disk, at most about three minutes old, is always there, five copies at most but for those until they settle, and nothing extra is written. A copy is read only when it is whole JSON, newest first by place (never `.part`); the store's read, or failing that the first save after it, deletes every copy newer than the one read. Files earlier builds left are read too: their checkpoints (`<key>.cp-<n>.json`, with no steady time), a `.prev` as the oldest, and `<key>.json` and `<key>.json.next` after every checkpoint and mark; then `<key>.json` goes when `.next` was read (as that build's next save would have taken it), any of them older than the one read that is not whole goes, and the rest are renamed to copies by those places. When a newer copy was torn and an older one opened, the app says so once over every screen until the person taps OK (`passedOverNewer`, `shutOffWhileSaving`, which is never saved). An older version's row is moved into a copy on the first read and stays in AsyncStorage until there is an anchor (at a save, or on a timer with the app idle), never at a read; while no copy is whole, the row is read. A phone with nothing of the records on it writes a clear mark before its first save, so that if a power cut tears every one of its first saves it opens as the build starts, never on Records not read. Before a save that empties the phone (`resetDemo`, which `clearDevice`, `forgetPhone` and `deleteMyAccount` with `clearPhone` use) or takes one person's account and hourly rate off it (`deleteMyAccount`, `deleteAccountWithPassword`), the store calls `forgetCopies` (`'clear'`, or `'drop'` with the account's id; the web's does nothing, as it keeps one copy): a copy a killed save left half written goes, an empty mark is written first (`<key>.cleared-<n>.json` or `<key>.dropped-<n>-<account id>.json`, its name the first place after it), and the marks go once a copy after them is the anchor. With no room for a new file, a clear's own save makes its mark of the oldest copy from before it: renamed to the mark first, so that it is never read again, then emptied; when it cannot do that either, that save is not written but held in memory and said, as any save the phone has no room for is, and the next save tries again. A drop's save with no room for its mark is not written either, but held and said the same way until a save can make the mark; a drop's mark is never made of a copy from before it, since the rest of the records are in those. No copy from before a clear is read again, and the clear's own save deletes every one: with nothing saved since whole, the phone opens as the build starts, never on what was cleared and never on Records not read, and says it shut off while saving when a copy after the mark was torn. The copies from before a drop go by the anchor rule, an older version's row with them. A power cut before a drop's save has settled can open on a copy from before it, with the shut-off notice, so that nothing else on the phone is lost; then `dropUndone` and `undoneDrops` say so and whose account it was, the store's read, or failing that the first save after it, renames the drop's mark `<key>.undone-<n>-<account id>.json` (every drop's, when it opened on an older version's row, which is older than them all), which says so at every later start and makes no copy count as after it, and the store makes the drop again by itself as it opens (`finishUndoneDrops`: the account, its session and its hourly rate off the phone, on the phone only, nothing asked of the server), whose `forgetCopies` takes that mark away. One it cannot make again because the account's shift is open in the copy it opened on is said over every screen until the person taps OK (`deletionNotFinished`, which is never saved), and again at each start until it is deleted again; a drop's mark that names no account (only an earlier test build wrote one) is said once, since the app cannot tell whose it was. Known limits, as randomized runs measured them, not bounds: a start of the phone that the next start of the app cannot see on the steady clock (it first reads the records past the time of the last copy before it), while the five copies are kept for other reasons, can make a power cut that tears the last two minutes of awake time open further back than it may, always on a whole copy and with the notice (14 of 374 runs of 200 short starts with sleeps, reboots and jumps of an hour either way, every one traced after two reboots close together: up to 4 saves, about 4.7 minutes of awake time and 6.4 hours of real time further back; `UNSEEN_REBOOT_SAVES` in `recordsLifetimes.test.ts`); and the copy before a nap with the app open is kept only with room to spare, and the copy before a nap under 5 s not for it at all, so that while the five copies are kept for other reasons a power cut that tears what was written since the phone last woke can open one save further back than it may, again whole and with the notice (2 of 60 runs of 150 starts of up to eight saves with naps of 2 s to 45 s, 13.5 s of awake time back, from 29 times in 13 runs before naps were counted). Under a React Native whose steady clock counted from the app's start, which `steadyClock.test.ts` rules out, nothing from an earlier start would be thinned or settled in a start under two minutes, and one that first read the records 10 s or more after the app started could take copies an earlier start wrote seconds before for settled. On the iPhone they stay in AsyncStorage, which keeps them out of the phone's backups. RNCAsyncStorage keeps a value of up to 1,024 characters in its manifest and a longer one, as the records soon are, in a file of its own named by the MD5 of its key (`Library/Application Support/<bundle id>/RCTAsyncLocalStorage_V1`); when it cannot read that file, it takes the key off the manifest it holds, answers null when asked again, and writes that manifest to the disk at its next change of any key, after which no start of the app reads the file through it again. So a read that fails writes nothing to AsyncStorage, and nothing else can before the app is opened again: the store writes nothing over records it has not read, and while it has not, the app shows Records not read and starts nothing else, the server session's client among it. When AsyncStorage answers null, the records' own file is read (`valueFileOf`, which finds the folder under Application Support rather than asking for the bundle id, and `md5` in `src/util/hash.ts`): whole JSON, it is the records, and the save the store makes as it opens lists the key again; there but not whole, the read fails. A save short enough for the manifest, and a removal, take away a file of the records that RNCAsyncStorage no longer lists, so it is never read in their place. With no file either, the mark beside the key decides (`<key>:on-this-phone`, inline in the manifest, written at the first save or read that works and never at one that fails, removed only with the records): with it there, or after a read of the key failed this session (`guardRecords`), the read fails, never a new phone; without it, it is a new phone. On the iPhone, as on Android, the Records not read screen says to tap Try again first, then to close MineMuster (swipe it away) and open it again. The server session stays in AsyncStorage on both (`safeStorage`, which falls back to memory one key at a time). In every build, the web's too (`guardRecords` in `src/services/recordGuard.ts`, which both storages use), nothing is written over the records or removes them until the store has read them (`recordsRead`), and records that could not be read or migrated show a message (`recordsUnreadable`, `RecordsUnreadableScreen`), never a new phone; a browser that will not let the app at its storage at all keeps them in memory for the session (`keptInMemory`), and in a build that keeps real records, not the preview (`DEMO_MODE`), says over every screen that they go when the tab closes (`recordsInMemory`, which is never saved). Every tab of MineMuster in a browser shares the browser's storage and saves the whole store on every change, so one tab at a time saves the records (`recordsTab` in `src/services/recordsTab.ts`, tested): the one holding an exclusive Web Lock named for their key, taken as it first reads them and held until it closes; with no Web Locks (no secure context), or a lock manager that turns the request down or does not answer, every tab saves until another tab's save of them reaches it (the `storage` event). A tab that does not save them is hidden behind MineMuster is open in another tab (`recordsElsewhere`, which is never saved; `RecordsNotSavedFrame`), so nothing is done there that is not saved, until Use this tab (`takeRecordsHere`, a steal: the tab it is taken from learns it from an AbortError and is hidden in turn) or the other tab closes; it then reads them again before it saves anything (`inAnotherTab`, `watchOtherTabs`). Meanwhile it sends nothing to the company either: `App.tsx` runs `startSync` only in the tab that saves them. Records a blocked storage keeps in memory are the tab's own and never wait on another. A phone has none of it (`storage.native.ts`). A save that cannot be written (a full phone or browser storage) is kept in memory and said over every screen until a save works (`recordsUnsaved`, which is never saved; `RecordsNotSavedFrame`, which saves again every 15 seconds meanwhile, and in a browser, whose room for a site is fixed whatever room the computer has, every 5 minutes after three tries in a row; a change still saves at once). In a browser these notices and `RecordsUnreadableScreen` speak of the browser, the tab and its site data, never of the phone or deleting the app. Screens call store actions; they do not write state directly. When the saved shape changes, raise `STATE_VERSION` and add the step to `migratePersisted` in `src/store/migrate.ts`, with a test. Version 10 added `receiving` (`Receiving` in `src/domain/receive.ts`), what a phone connected to its company keeps about receiving from it; a phone connected before version 10 starts reading the company's records from the beginning.
- **The office dashboard (`dashboard/`) runs the phone's own rules.** It imports `src/domain` through its `@app` alias, and a test and the build stop shared code from importing React Native or Expo. A rule both sides need (adding a unit in `src/domain/fleet.ts`, a sheet in `areaExam.ts`, the company form in `companyForm.ts`) lives in `src/domain` and the store calls it: never copy one into the dashboard. The dashboard's Fleet, Exam sheets and Company pages write the same `equipment`, `areaSheet` and `settings` records a supervisor's phone sends, and the Roster page the `employee` records, through `push_records`, with `revOf` and the version they loaded as `base`. Phones receive what the Roster, Fleet, Exam sheets and Company pages save the next time they are open with signal, and those pages say so. The Roster page is where people are changed: it writes the sign-in row and the person in the app together (`dashboard/src/lib/rosterPeople.ts`). Phones do not receive time, leave, checklists, equipment use, exams or requests, and no page says they do.
- **Supervisors deal with sign-ins on the dashboard's Roster page, not in the app.** Its Account column says how each row is held (`roster_sign_ins`, `accountWords` in `dashboard/src/lib/signIns.ts`): Not joined yet, Joined with a passcode, Joined with email, Locked until a time, Locked, needs a reset, or Invited, waiting to accept (or, with `invitation_lapsed`, that the invitation needs to be sent again because the supervisor who sent it is no longer one). **Reset passcode** on a passcode row makes a reset code, shown once, with what to tell the person. **Delete sign-in** deletes a crew sign-in for good through `supervisor-tools`: the row and every record stay with the company, the link to the account is cleared and every session of the account ends; it is also the fix for someone who signed up under a coworker's name. **Invite by email** on a supervisor's row with no email account records an invitation and puts nobody on the row: it is good for 7 days, one is open for a row (a new one cancels the one before), a supervisor can Send again or Cancel it, and the invited person takes the row only by accepting, signed in with the invited address once Supabase Auth has confirmed it, while the supervisor who sent it is still one (`accept_supervisor_invitation`). The inviter always gets the same answer ("Invitation sent to ..."), whether or not the address has an account. **Make a supervisor** on a passcode row opens the invite, since a passcode account never holds a supervisor's row; accepting lets the passcode account go. The invite link's landing (`readArrival` in `dashboard/src/lib/supabase.ts`) takes a session from the address only for an invitation (`invited=1` and `type=invite`), tidies any session out of the address before the client is made, and names the signed-in address first ("Set a password for ...", with "This is not my email: sign out") so a link someone else wrote does not go unseen; every other link stays PKCE code-only. The crew page (`EmployeeScreen`) is read only by an email account that holds a crew row: it says to tap Supervisor? Sign in with email on the app's first screen and sign in with the same email. New crew sign up in the app with the company code, their name and a passcode. "Company code" is what a person reads, in the app and on the dashboard; the code's identifiers keep `joinCode`.
- **Platform splits use file suffixes**: `notifications.native.ts` / `notifications.ts`, `saveFile.native.ts` / `saveFile.ts`. The plain file is the web version and the source of the shared types.
- **Icons are imported one file at a time** through `src/components/icons.ts`. Importing from the `lucide-react-native` root pulls the whole library into the bundle.
- **Fonts are imported one weight at a time** (`@expo-google-fonts/barlow/500Medium`), for the same reason.

## Design

- Palette, type and spacing are in `src/theme/theme.ts`. Build screens from `src/components/ui.tsx`; do not hand-roll buttons or inputs.
- A record is shown as the paper it replaces: the day's equipment card (`ChecklistCard`), an exam (`ExamSheet`) and a maintenance request are built from `src/components/Paper.tsx`. Printed words are condensed capitals; what a person wrote in is the ordinary text face.
- **The company is a setting** (`settings.company`: name, state, place, logo, pay schedule; `src/domain/company.ts`). A supervisor changes it on More → Company (`setCompany`); a build can start with its own in `EXPO_PUBLIC_COMPANY`. Do not write a company's name, place or schedule into code or copy; read the setting. Everything hours and pay is before taxes.
- **The clock-in site is a setting too** (`settings.site`, `src/domain/site.ts`): a pin, a radius and an optional town to measure from. A build names its own with the company (`site` in `EXPO_PUBLIC_COMPANY`); a supervisor puts the pin where they stand on More → Mine boundary (`setSitePin`). The sample company's site is made up (`SAMPLE_SITE`). With no site, a clock-in is turned down and the crew board says so; clocking out and lunch are never blocked. Never write a mine's location, address, parcels or permit into code, tests or docs: the old built-in pin is known to the migration only by its hash.
- **MineMuster's own logo** (the silver MM over MINE MUSTER) is made from the renders in `assets/brand/source` by `scripts/make-brand-assets.py`: the sign-in logo, the app icon, the Android adaptive and themed icons, the launch image, the favicon, Android's notification icon, and Google Play's listing icon and feature graphic (`assets/store/`). Remake them with the script; do not edit them by hand, recolour them or set the name in a font instead. The logo is made for dark backgrounds (its black is transparent): never put it on a light one. The app icon, launch screen and browser tab are MineMuster's for every company.
- **A company's logo is shown only when it has one.** Draw it with `CompanyLogoPlate` from `src/components/Brand.tsx`, always on white; with no logo it draws nothing and the screen keeps its plain colour (the sign-in screen shows `MineMusterLogo`). U.S. Mine Corp.'s logo is the built-in traced art (`logo: { art: 'us-mine' }`, drawn by `Logo`): do not redraw it, recolour it, stretch it, set it in a font, or edit the generated `src/components/logoArt.ts` by hand. A store build leaves the art out (`EXPO_PUBLIC_LOGO_ART=0`; `HAS_LOGO_ART` in `src/components/Brand.tsx`, behind a condition the bundler folds, as the server code is): a public app carries no customer's trademark, and a company whose logo is the art shows none there.
- Tap targets are at least 56 px. The crew works in gloves and in sunlight: large type, strong contrast, light backgrounds.
- The top of the Clock screen takes the colour of the person's status (off, on, at lunch, overdue). Do not reuse those field colours for decoration.
- Copy is plain and in sentence case. Buttons say what happens ("Clock in", "Send maintenance request"). Errors say what went wrong and what to do next.

## Privacy and safety rules that must hold

- **This repository is public.** Never commit a real person's name, contact details, pay or any other personal detail: not in code, tests, `src/store/seed.ts`, commit messages, screenshots or sample workbooks. The sample crew is made up and stays that way. The person a build is made for is named in `.env.local` (`EXPO_PUBLIC_ROSTER_OWNER`), which git ignores, and so is the mine's whole roster (`EXPO_PUBLIC_ROSTER`: names and job titles, nothing else); `withBuildRoster` in `src/domain/roster.ts` puts them on the roster.
- **Nothing is made up for a real person.** Everyone a build names starts with no hours, no checklists, no exams and no requests. The sample history belongs to the made-up crew (`SAMPLE_CREW_IDS`). Never move a sample record onto anyone else, however much better a demo would look with real names on it.
- **A build that names its roster has nobody made up in it** (`SAMPLE_CREW` in `src/config.ts`, decided by `startsWithSamples`). It starts from `buildBareData`: the fleet and the area sheets, the build's own people, and nothing that happened. There is no sample person to open it as, so the sign-in screen offers `openAsOwner` and nothing else, and the reset on the More screen clears the device instead of reloading samples. Check `SAMPLE_CREW`, not `DEMO_MODE`, before assuming a sample person or a sample record is there. A build that connects (`EXPO_PUBLIC_DEMO=0`) starts from `emptyData` instead: no fleet, and nobody on the roster but the people it names. Once a phone has been connected to a company (`syncedWith`), `ensureSeeded` no longer adds the build's own people and sheets at start-up, until the device is cleared. The ones it added before then stay on the phone beside the company's: the merge changes only what the company sends, and a phone whose company sign-in is a supervisor's sends the company any of the build's sheets the company does not have.
- **The samples can be kept beside a real roster** with `EXPO_PUBLIC_SAMPLE_CREW=1`, for showing the app with history in it. The Roster screen then marks the made-up people "Sample", and none of them keeps the last name of someone the build names: `buildDemoData` is told who the build names and `keptApart` gives that sample person a spare one. Tests compare the sample crew with `.env.local` wherever that file names a roster.
- **Sample data and people's own records are saved apart.** A store that holds the sample crew is saved under one name and reloads its samples when the saved shape changes; a store without them is saved under another and keeps every record (`HOLDS_SAMPLES` in `src/store/useStore.ts`). A build with no samples must never open onto sample data an earlier preview left on the device.
- **A typed name is matched to the roster in one place**, `findOnRoster`. The roster holds a name the way the mine writes it; a person may leave off a middle initial or a "III", or go by the nickname in quotes. A name that fits more than one person is turned back with a request to type it as it is on the roster. Do not match on a first name or an initial alone.
- **The mine's own area sheets stay out of the repository too.** They list the plant's equipment. They go in `.env.local` (`EXPO_PUBLIC_AREA_SHEETS`) or are typed into the app, never into code, tests, the sample data or anything in `docs/`. Build what goes into `docs/` with the private settings empty (`EXPO_PUBLIC_ROSTER_OWNER= EXPO_PUBLIC_ROSTER= EXPO_PUBLIC_AREA_SHEETS= EXPO_PUBLIC_SAMPLE_CREW= EXPO_PUBLIC_COMPANY= EXPO_PUBLIC_SUPABASE_URL= EXPO_PUBLIC_SUPABASE_KEY= npx expo export --platform web --clear`).
- Location is read only at the moment of a punch. Never add background location.
- A punch that is turned down is logged; clock-out and lunch start are never blocked by location.
- A clock-in with no location (location off, approximate only, or no fix) goes through with `noLocation` on the punch and the `no_location` flag for review. It is never turned down for want of a location, and nothing is paid or docked for it. A clock-out or lunch start with no location carries `noLocation` too when a boundary is set, and is not flagged. A clock-in with a position outside the boundary, a simulated one, or one too vague to trust (over 200 m) is turned down and logged, by the store (`clockInTurnDown`) as well as the Clock screen (`clockInVerdict` in `src/domain/geofence.ts`); with no boundary set, none goes through. With only an approximate location no position is read at all, and the Clock screen never sends anyone to the phone's settings to get a clock-in through. Check where I am on the boundary screen is a supervisor's: the crew's location is read only when they punch.
- Punch times are never silently changed. A correction needs a reason and is appended to the shift's edit history.
- A lunch runs the full 30 minutes. It cannot be cut short from the phone, and no location is read when it ends.
- The notice that lunch is over is always sent. The Lunch reminders setting only covers the reminders before the lunch deadline.
- Lunch flags are for review. Nothing is paid or docked automatically.
- Nothing is signed with a line left blank, or with a Bad Order that does not say what is wrong. That holds for the equipment checklist and for the pre shift exam, in the store as well as on the screen.
- A condition found on a pre shift exam stays open until a date fixed is recorded. Only the person who made the exam or a supervisor records one by hand; completing the maintenance request it was sent on records it too.
- A maintenance request is assigned by a supervisor, and worked by a supervisor or the person it is assigned to. It is not completed without remarks. "Completed by" is the person who closes it; a supervisor closing it out for the person it is assigned to may name that person instead, and nobody else.
- A maintenance request points only at what is there: a unit in the fleet, a checklist made on that unit, a Bad Order on an exam that is still open and has no request yet. The same words about the same unit or place from the same person, while their first request is still open and asks for as much, are not sent twice (`createMrf`); a checklist sent that way goes on the open request instead (its `mrfId`), so its result screen goes on as after a send. One that asks for more, a red tag or a higher priority, is a request of its own. The result screen holds Android's back button for a request only while one can be made from it (`requestTargetProblem`).
- Nothing closes a condition except its own date fixed. The same line found again on a later exam is a record of its own, and marking the line OK later does not close it. The app tells the person; it never closes one for them.
- A danger is shown as a danger wherever its area is: the area list, the area's sheet, the exam form and the Crew board, ahead of anything else that is open.
- A shift with no clock-out counts no hours anywhere until a supervisor sets its end. Payroll, the equipment card and the exports agree on that.
- An hourly rate is entered by the person it belongs to, for their own pay estimate. It is never shown to anyone else, never goes in an export and never leaves the phone: `changesToSend` has no way to reach `payRates`, the accounts or the passwords on the phone, and the server refuses a record that carries them.
- A phone sends the company's records (punches, leave, checklists, equipment use, exams, requests, the fleet, the area sheets and the shared company settings) only to the company it is connected to, and only from a build with no sample crew in it. The phone's own settings stay on it.
- On a phone connected to its company, people are added, taken off and given a role or a payroll ID only on the dashboard's Roster page: the store refuses each of those changes, and the phone never sends a person. A payroll ID reaches a connected phone only while its company sign-in is a supervisor's: the server leaves payroll IDs out for any other account, the merge stores none on a phone whose sign-in is not a supervisor's, and the phone takes every one off when a standing read finds its sign-in crew or off the roster (`mergeRows`, `standingChange`).
- On a connected phone a person has a supervisor's powers only when their record says supervisor, the phone's company sign-in is a supervisor's, and that sign-in is theirs (`supervisorHere` in `src/domain/access.ts`, which the store and `useSupervisorHere` both call). One person per phone: only the person the phone's company sign-in is for has an account on it, opened by itself once the phone has read the company's records to the end (`openOwnAccount`, `receiving.caughtUpAt`; `ownPersonHere`, `accountHere`). The phone keeps neither a password nor a passcode.
- **Deleting an account removes the sign-in and what is the person's alone.** More → Delete my account deletes the app's sign-in and the hourly rate, and the person's company sign-in when it is theirs: the one the phone sends with, when the company says it is theirs, or, on a phone that never joined, the one signed in under the app account's own email. A company sign-in alone is deleted from the company sign-in screen's cards, and nothing of the app's: Delete this sign-in for an email sign-in on no company's roster (`DeleteAccount` with `signInOnly`), Delete my account for one taken off the roster (`whoseSignIn`, `deletionPlan` in `src/domain/accountDeletion.ts`, tested). A passcode account is deleted with its passcode, typed again: `confirm` through `crew-auth` checks it against the account signed in on the phone (a wrong try counts against the account's lock, and no code or name is sent), and answers a session made just now, then `delete-account` runs unchanged; an email sign-in is deleted with its password as before. Someone taken off the roster can still sign in, only to delete their own account. A company sign-in signed out of the server on the phone is not deleted from it: the app says to sign in again first, or that a supervisor deletes a passcode sign-in on the dashboard, and never says something was deleted when nothing was. The company's records and roster rows stay with the link to the account cleared, and the app says what stays and why before anything goes. The phone is cleared only when nothing on it would be lost: no other account, everything reached the company, and the company's records read to the end. Once its own sign-in is deleted, the phone forgets who that sign-in was (`signInGone`). An answer that does not say whether the sign-in went is checked with Supabase Auth before the phone says anything, and the app never says nothing was deleted when nobody can tell. An account made in the app on another phone stays on that phone. Nobody on the clock and no sample person is deleted.
- Nobody on the clock is signed out for being taken off the roster: a person off the active roster, or the person a phone's sign-in is for once that sign-in is off the company's roster, keeps the Clock screen, not the tabs, until they clock out (`signedInView`). `clockIn` turns down a person off the active roster, and anyone on a phone whose sign-in is off the company's roster.
