# MineMuster database

This is step 1 of MineMuster, the version of the crew app that more than one company can use. It is the shared database underneath: the companies, the people on each company's roster, how a person's account joins their company, and who may see and change what. It is written for a Supabase project (PostgreSQL with Supabase Auth and its API). Step 2 adds the records the crew's phones send: see [The records](#the-records). Step 3 adds what a company pays through Stripe and the contact form on minemuster.com: see [Billing](#billing) and [The contact form](#the-contact-form). Step 4 adds how the crew get in with no email, a company code, their name and a passcode, and how a supervisor invites another supervisor from the dashboard: see [Crew sign-in](#crew-sign-in) and [Supervisor invitations](#supervisor-invitations).

The app and the office dashboard (https://app.minemuster.com) connect to the MineMuster Supabase project, where these migrations are being applied in order: check which have run (`supabase migration list`, or the project's migrations page) before counting on one. Everything here is tested on a local database on this machine, and the rules that only show when two requests overlap on a throwaway local PostgreSQL server.

- `migrations/` holds the SQL migrations, applied in order of their file names.
- `functions/` holds the edge functions: `stripe-webhook`, where Stripe sends its events (see [The webhook](#the-webhook)), `delete-account`, where a person deletes their own sign-in (see [Deleting an account](#deleting-an-account)), `crew-auth`, where the app signs a crew member up and in with a passcode (see [The crew-auth function](#the-crew-auth-function)), and `supervisor-tools`, where the dashboard invites a supervisor and deletes a crew sign-in (see [The supervisor-tools function](#the-supervisor-tools-function)). `functions/_shared/server.ts` reads the project's address and keys for all of them, and `functions/_shared/http.ts` is how `delete-account`, `crew-auth` and `supervisor-tools` read their requests and make their calls to Supabase Auth and the database, each given 15 seconds, with the gate on the dashboard's origin that `delete-account` and `supervisor-tools` share.
- `tests/` holds the tests, which run the migrations on a fresh local PostgreSQL ([PGlite](https://pglite.dev)) and try every rule as the API roles would.
- `checks/` holds `shared_shapes.sql`, a read-only check to run on a project before migration `20261120000100` is applied there (see [Applying the migrations](#applying-the-migrations-to-a-supabase-project)).
- `tools/` holds `make_name_skeleton_table.py`, which makes the table of look-alike characters in `20261116002500_lookalike_names.sql` from Unicode's `confusables.txt` (see [How a typed name is matched](#how-a-typed-name-is-matched)).

The names in the tests and on this page are made up. The repository is public: keep it that way.

## The tables

The four tables below are in schema `public`, and row level security is on for every one of them. Two more there hold what the functions keep for themselves, and neither `anon` nor `authenticated` may read or write them: `company_supervisor_guard`, the row the last-supervisor guard writes for each company whose supervisors change (see [A company always keeps a supervisor](#a-company-always-keeps-a-supervisor)), and `join_holds`, the accounts a supervisor has acted on in a company (released, barred, or both, one row for each; see [How someone joins](#how-someone-joins)). The records the phones send are in two more, `records` and `record_history`, and `push_records` keeps its own counts in `record_counters` and `record_usage` (see [The records](#the-records)). Billing is in `billing_subscriptions`, `billing_overrides` and `stripe_events` (see [Billing](#billing)), and the website's contact form in `contact_requests`, with `contact_senders` and `contact_sender_key` for its limit on each sender (see [The contact form](#the-contact-form)). Crew sign-in keeps `crew_key`, the key every passcode digest is made with, `crew_logins`, a row for each crew account with its digest, its wrong tries and its lock, and `crew_sign_in_tries`, the rows its limit on tries counts (see [Crew sign-in](#crew-sign-in)), and supervisor invitations are in `supervisor_invitations` (see [Supervisor invitations](#supervisor-invitations)); no API role, the server key included, reads or writes those four. None of the twenty keeps planner statistics (see [What a count can tell](#what-a-count-can-tell)).

### companies

One row for each company that uses the app: a mine, a plant or a contractor.

| Column | What it is |
|---|---|
| `name` | The company's name, 1 to 120 characters once trimmed. Runs of spaces are closed up. |
| `join_code` | The code a new person types to find the company. Unique. See [Join codes](#join-codes). |
| `state` | The two-letter postal code of the state whose hours rules the company follows: one of the 50 states or `DC`. |
| `timezone` | The IANA time zone its days and pay periods are counted in, such as `America/Los_Angeles` (the default). It must be one the database knows. |
| `logo_path` | Where the company's logo is kept in storage. Optional: null means no logo. A file in the company's own storage: no `..` segment, no leading `/`, no backslash and no hidden characters. Storage should still build the full path from the company's id. |
| `pay_period` | The company's pay period rule, as a JSON object of at most 16 KiB as text. Null means none is set. The shape of the object is the app's to define. |
| `created_by` | The account that started the company. Cleared if that account is deleted. |
| `created_at`, `updated_at` | When it was made and last changed. `updated_at` is kept by the database. |

### roster

Everyone who works for a company, written the way the company writes their name. A supervisor puts people on it. A person's account claims their row when they join, and from then on that row is them in that company.

| Column | What it is |
|---|---|
| `company_id` | The company. A row never moves to another company. |
| `first_name`, `last_name` | The name as the company writes it, which can carry a middle initial, a nickname in quotes or a suffix: `Riley J` `Quinn`, `Lee "Buck"` `Vance III`. |
| `title` | Job title. Optional. |
| `role` | `employee` (the default) or `supervisor`. |
| `active` | False once the person is taken off the roster. An inactive row is never matched to a typed name, and its account is no longer a member. |
| `inactive_since` | When the row was taken off the roster; empty while it is on it (a check holds the two together). Written by a trigger alone, from `20261120000200`, and kept as it is while the row stays off: closing a company waits 30 days after the last person was taken off (see [Deleting an account](#deleting-an-account)). |
| `user_id`, `claimed_at` | The account that claimed the row, and when. Only the functions write these. |

A row is claimed by one account at a time, and a claimed row is never handed straight to another account: a supervisor releases it first (`release_roster_claim`), or approves the right person's request onto it with `replace_claim`, which does both in one step. Deleting an account lets go of its rows. One account holds at most one row in a company, active or not, and may belong to several companies.

### join_requests

When someone with the company's code types a name that is not on the roster, or a name whose row another account has already claimed, the database leaves a request for the company's supervisors. A supervisor approves it or denies it.

| Column | What it is |
|---|---|
| `company_id`, `user_id` | The company, and the account asking to join. |
| `first_name`, `last_name` | The name as the person typed it, trimmed. |
| `reason` | Why the name did not join by itself: `not_on_roster` (no row fits the name), `already_claimed` (the one row it fits is another account's), `supervisor_row` (the one row it fits has the supervisor role, never handed out by a typed name), `removed` (the caller was taken off this roster), `released` (a supervisor released the caller's claim here, or deleted the caller's row), or `ambiguous` (the name is written the same way for several people, so no typing can single one out). |
| `status` | `pending`, then `approved` or `denied` by a supervisor, or `withdrawn` when the account joined by itself or was taken back on its old row while the request waited. A withdrawn request is kept, with its notification, and is decided: it can be neither approved nor denied. |
| `roster_id` | The row the request was approved onto. |
| `decided_by`, `decided_at` | The supervisor who decided, and when. |

An account has at most one pending request per company. After a denial the person may ask again, which makes a new request, unless the supervisor denied it with a bar.

### notifications

What a company's supervisors are told: `joined` when someone joins by claiming their row (`roster_id` says which), and `join_request` when a new request is left (`request_id` says which). Every supervisor of the company sees the same notifications, and `read_at` is shared: when one supervisor marks a notification read, it is read for all of them. Approving or denying a request writes none: the request already has its own. A request that is withdrawn keeps its notification, so the supervisors still see, for instance, that an account first typed a claimed coworker's name and then an unclaimed one. A notification goes when the row or request it points at is deleted.

## Join codes

- A code is eight characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`: capitals and digits without the look-alikes 0, O, 1 and I. That is 32 characters, so there are about 1.1 trillion codes.
- The database makes them. The randomness comes from `gen_random_uuid()`, which draws on the server's cryptographically strong random source. Each character takes one wholly random byte of a fresh UUID. Since 256 is a multiple of 32, no character is likelier than another. A code already in use is drawn again.
- Codes are read the forgiving way: capitals or not, with spaces or dashes anywhere (`abcd-2345`, `ABCD 2345`). En and em dashes count as dashes, because phones turn a typed hyphen into one.
- People read "company code" in the app and on the dashboard; the column and the functions keep `join_code`.
- A supervisor can give the company a new code with `rotate_join_code`. The old code stops working at once. Everyone who already joined stays on the roster.

## How someone joins

1. **A supervisor starts the company.** They sign in and call `create_company` with the company's name, state and time zone and their own name and title. The database makes the company, puts them on its roster as a supervisor with their account on the row, and hands back the company's id and join code. One account starts at most 3 companies in any 24 hours and 20 in all (migration `20261117000800`, below).
2. **The supervisor puts the crew on the roster** and shares the company code with them.
3. **A person signs up and types the code.** The app's first screen asks the `crew-auth` function to look the code up (`crew_lookup`) as it is typed, and shows the company's name and state under it, such as "Test Pit A (CA)", so a wrong code is caught first. It gives the company's name and state and nothing else. `company_by_code` itself is for signed-in accounts (the dashboard calls it): nobody signed out can try codes except through `crew-auth`, under its limit.
4. **They type their name.** For a crew member the `crew-auth` function makes their account and calls `join_company` as it, with the code and the name, so every rule here applies unchanged (see [Crew sign-in](#crew-sign-in)). An account that signs in with email calls it directly. It answers with one of these:

| Status | What happened | What the app does |
|---|---|---|
| `no_company` | No company has that code. Nothing is recorded. | Ask them to check the code. |
| `already_member` | Their account already holds an active row there. `role` says which. | Open the company. |
| `denied` | A supervisor denied this account with a bar. Nothing is recorded, and no notification is sent. | Tell them a supervisor has turned the request down, and to speak to one. |
| (refused, `22023`) | The name only looks like a name on the roster: no row of the company is it or fits it, but one does once both are read for the characters they look like (see [How a typed name is matched](#how-a-typed-name-is-matched)). Nothing is recorded. | Ask for the name the way it is written on the roster. |
| `joined` | The name is exactly one active, unclaimed **employee** row. It is now theirs, `role` says which, and the supervisors get a `joined` notification. Any request of theirs still pending there is settled as `withdrawn`. A supervisor row is never claimed this way; it becomes a `pending` request instead, and so does any name typed by an account that was taken off the roster or whose claim was released. | Open the company. |
| `ambiguous` | The name only loosely fits several rows and none exactly, so typing the whole name as it is on the roster would settle it. Nothing is recorded. | Ask for the name the way it is on the roster. |
| `pending` | A request is waiting for a supervisor. `reason` is `not_on_roster`, `already_claimed`, `supervisor_row` (the row it fits is a supervisor row), `removed` (the caller was taken off this roster), `released` (a supervisor released the caller's claim, or deleted the caller's row), or `ambiguous` (the name is written the same for several people). The supervisors get a `join_request` notification. Trying again while it waits returns the same request and adds nothing. | Tell them a supervisor will let them in. |

Every answer but `no_company` carries `company_name`.

5. **A supervisor decides the request.** `approve_join_request` either puts the person on a row already on the roster (`roster_id`, which must be active and unclaimed, unless `replace_claim` is given; see step 6) or makes a new row from the name on the request, with the given `role` and `title`. `deny_join_request` closes it; with `bar`, it also turns the account away from the company from then on (`join_company` answers `denied` and records nothing) until a supervisor calls `lift_join_bar` with any of that account's requests. A bar holds in that company only, and is kept apart from a release (step 6): lifting the bar leaves an account whose claim was released still held, so it may ask again but still takes no row by typing a name. A request is decided once.
6. **When the wrong account has a row** (someone typed a coworker's name), the simplest fix is one step: approve the right person's request onto that row with `replace_claim`, which lets go of the wrong account and gives the row to the right one in the same transaction, so nobody with the code can take it in between. A supervisor can also call `release_roster_claim` on the row; the right person can then join by typing their name if it is an employee row, or a supervisor approves their request onto it. Either way the account the row was taken from is held: it can no longer take any row by typing a name, and typing one leaves a `released` request. The same goes for an account whose row a supervisor deletes. Approving one of its requests lets it in and lifts the hold. A released **supervisor** row is never re-claimed by a typed name either: typing it leaves a request to approve.

Claiming locks the row and takes it only while it is still unclaimed, so two people can never claim the same row. The one who comes second gets a `pending` request with reason `already_claimed`. Once the row is locked the name is matched again, so a row a supervisor renames while its old name is being typed is not handed out under a name nobody typed. Calls by one account to one company take turns, with each other and with a supervisor approving or denying that account's request, so someone who types a name while their request is being approved is told `already_member`. They also take turns with a supervisor's change to the caller's own row in that company (releasing it, deleting it, handing it to someone else, taking the person back): `join_company` locks that row before it reads anything about the caller, so it sees such a change whole, never half of it.

A person who was taken off the roster (their row made inactive) is not let back in by themselves: typing their name — or anyone's — leaves a `removed` request, so a supervisor decides. Releasing or deleting their old row does not change that: they are held, and their requests say `released`. Approving it puts them on the given row (or a new one) and lets go of their old inactive row, because an account holds one row per company. To take someone back on their old row instead, a supervisor makes that row active again; the request they left while they were off is then settled as `withdrawn`, so it cannot be approved after a later removal.

### How a typed name is matched

These are the same rules as `findOnRoster` in `src/domain/roster.ts`. The tests hold the two together: they run every case in its tests, then compare the database with `findOnRoster` itself on more than a thousand typed names, and on Greek names typed in capitals. Outside that, the app still has to catch up with three things the database does: compose a name (`normalize('NFC')` in `cleanText`), fold a capital I with a dot (U+0130) to I before `toLowerCase` and a final sigma to a medial one after it, and count a word's length in code points (`[...word].length`) for the rule on initials. A test marked `todo` in `names.db.mjs` shows where the two still differ until `roster.ts` does the same.

- A name typed exactly as it is on the roster is that person. It is composed first (Unicode NFC, so an accent typed as a separate mark is the same letter), spaces at either end are trimmed, runs of spaces closed up and capitals ignored. A capital I with a dot counts as I, and a final sigma as the sigma it is.
- Otherwise the last names have to agree, give or take a suffix (Jr, Sr, II, III, IV, V), and every word of the typed first name has to be one of the words of the roster's first name. So `Riley` finds `Riley J Quinn`, and `Buck` or `Lee` finds `Lee "Buck" Vance III`. Words are compared in lower case, with quote marks (straight or curly), full stops, commas and hyphens taken out.
- A typed first name made only of single letters, such as `J`, is not a name.
- Only active rows are matched and claimed. The server looks for the exact match over every row of the company first, active or not, and runs the looser fallback only when no row is the name exactly and no *inactive* row fits it either: so typing a removed person's name, exactly or the looser way (`Riley J.` for `Riley J`, a suffix left off), never stands in for a different, still-active person, and leaves a request instead. (The app only ever matches active rows; this is a server-side guard the app cannot reach.)
- When a name is typed exactly as one row, the rows it only fits do not count: `Lee Park` is Lee Park even with Lee Roy Park on the roster. When it fits several rows and none exactly (`Roy Park` with Lee Roy Park and Roy "Lee" Park), it is ambiguous. When several rows are written the *same* way, so no typing can single one out, `join_company` leaves an `ambiguous` request for a supervisor instead of recording nothing.
- A name may not hold a control character or an invisible one: any of Unicode's default-ignorable characters (a zero-width space, a bidi override, a soft hyphen, a variation selector, a tag character, a Hangul filler, ...) or another format character. Nor may a name, first and last together, mix letters of the Latin, Greek and Cyrillic alphabets, which have look-alikes of each other; a name wholly in one of them is fine. Such a name is refused (`22023`), so a request cannot pose as a claimed coworker's name with a hidden or look-alike character in it. These rules hold for typed names, roster names and titles (and hidden characters for company names), and are checked when a name is written, so a rule made stricter later never blocks other changes to an older row.
- A name that only *looks* like a name on the roster is refused too (`22023`), whatever alphabets it is written in: `Joe Cox` written wholly in Cyrillic look-alikes, a small capital O or a Roman numeral fifty among Latin letters, a mathematical or fullwidth letter, a capital I for a small l, `rn` for `m`, an Armenian or Cherokee look-alike. Names are compared by what they look like (`name_skeleton`, after Unicode's confusables, UTS #39): compatibility forms folded (NFKC), every character Unicode lists as looking like a Latin letter, a quote mark, an apostrophe, a hyphen, a full stop or a comma read as it, `rn` read as `m`, and then capitals ignored, keeping a capital L apart from the small l that I, 1 and | look like (so `Lan` is not `Ian`). `join_company` refuses a typed name that no row of the company, active or not, is or fits, but that one is or fits once both are read that way; nothing is recorded. The roster refuses a name, when it is written, that looks the same as another row of the company without being written the same, so approving such a request cannot put a second row on the roster that reads the same. Two rows written exactly the same stay allowed. Two different people whose names only look alike (`Arnie` and `Amie`, say) are told apart on the roster some other way, such as a middle initial. The table of look-alike characters is made from Unicode's `confusables.txt` by `tools/make_name_skeleton_table.py` (`python3 -I tools/make_name_skeleton_table.py confusables.txt`) and is never edited by hand: a new table goes into a new migration that replaces `name_skeleton`. A look-alike Unicode does not list remains possible, so the app should still show a supervisor each request's `reason`.

### What the join code does and does not protect

The code is what keeps strangers out: without it, nobody can find a company or ask to join. Anyone who has it can claim an unclaimed **employee** row by typing that person's name, so a coworker could take another's row. The supervisors are told of every claim (`joined`) and can release one that is wrong. Rotate the code when it has gone further than the crew.

When the whole crew gets the code at once, as on a training day, have each person sign up with a supervisor watching. The supervisor checks the Account column of the dashboard's Roster page (Not joined yet, Joined with a passcode) against the room, uses Delete sign-in on any row the wrong person signed up on, so the real person can sign up for it, and uses Make a new code after the meeting.

A **supervisor** row is never handed out by a typed name, whatever code the caller has: a match onto one leaves a `supervisor_row` request for an existing supervisor to approve. So the code alone makes nobody a supervisor, and the company cannot be taken over by claiming an unclaimed supervisor row. A person taken off the roster leaves a `removed` request rather than walking back in, and an account whose claim was released a `released` one. A supervisor can keep one account out, short of rotating the code, by denying it with a bar. A **Supabase anonymous sign-in** (a throwaway account) is refused by `join_company` and `create_company`, so anonymous sessions cannot claim rows or flood requests if the project turns anonymous sign-ins on.

With the code, typing a name also tells a person whether such a name is on the roster and already claimed. An `ambiguous` answer names nobody.

Guessing a code means searching a space of about 1.1 trillion (32^8). Every company shares that one space, so a single guess finds *some* company with probability N/32^8 for N companies, not 1/32^8: a stranger looking for any company at all needs on the order of 1.1 trillion / N guesses, fewer as more companies sign up. A signed-out phone looks a code up through `crew-auth`, which counts every request against the caller's network address (at most 30 in 10 minutes: see [Crew sign-in](#crew-sign-in)), and signed-out callers can no longer call `company_by_code` at all. Lookups and joins by a signed-in account are not limited by the database, on purpose: the account is the barrier, and a company-wide slowdown would let one person lock the whole crew out.

It is never put in the app; the webhook holds it. |

Membership is always worked out from the roster: `is_member(company_id)` and `is_supervisor(company_id)` look for the signed-in account on an active row, and only while Supabase Auth has neither soft-deleted the account (`deleted_at`) nor banned it (`banned_until` still to come), the same test the last-supervisor guard counts by. So an account that is banned or soft-deleted loses every power at once, in every company, even though an access token it already holds stays valid until it expires: it reads nothing, changes nothing and calls no supervisor function, and `join_company` and `create_company` refuse it (`42501`). The row level security policies compare each row's company with the caller's own companies (`member_company_ids()` and `supervisor_company_ids()`, by the same rule), worked out once per statement. Each of these functions reads the caller's id once per call, as `(select auth.uid())` (migration `20261117000700`), not once for each roster row it reads.

These are never written through the API, by anyone, supervisors included: `user_id`, `claimed_at` and `inactive_since` on the roster, a row's `company_id`, a company's join code, id, creator and dates, anything in `join_requests` or `notifications` except `read_at`, and anything in `company_supervisor_guard`, `join_holds`, `records`, `record_history`, `record_counters`, `record_usage`, `billing_subscriptions`, `billing_overrides`, `stripe_events`, `contact_requests`, `contact_senders`, `contact_sender_key`, `crew_key`, `crew_logins`, `crew_sign_in_tries` or `supervisor_invitations`. Column privileges refuse the write outright ("permission denied"), rather than quietly ignoring it.

A member of one company sees and changes nothing of another, in any table or through any function. A function asked about another company's request, row or company gives the same "not found" error as for an id that does not exist.

### What a count can tell

Row level security hides rows, not the planner's statistics, and PostgREST answers a request made with `Prefer: count=planned` (supabase-js: `select(..., { count: 'planned' })`) with the planner's row estimate for the caller's own query. With ordinary statistics that estimate is worked out from every company's rows: it would tell a real company id from a made-up one and roughly how many people it has, confirm that a surname is on another company's roster, and give up other companies' ids to anyone who bisects `company_id < X`. So no column of any table here keeps statistics (`set statistics 0`, migration `20261116002200`, and `20261117000100` for the records), and every estimate is the planner's fixed default. What an estimate still reflects is a table's total number of rows across all companies, never one company's. Statistics already gathered survive turning them off, which is why this lands with the tables, before they hold data.

Nor does how long a request takes depend on another company's rows. A policy that called a function on each row it met (`is_member(company_id)`) read every company's rows for a request with no filter of its own, and took longer the more hidden rows fit the caller's filter: response times told a real company id from a made-up one and roughly how many people it has, confirmed a surname on another company's roster, and gave up the leading digits of other companies' ids to anyone who bisected `company_id < X`. Each policy is now a comparison of the row's company with the caller's own companies, worked out once per statement (`company_id = any ((select public.member_company_ids())::uuid[])`, migration `20261116002300`). PostgreSQL uses it as an index condition, so rows of other companies are not read at all (`row_reads.db.mjs` checks the plans and the times). What remains is small: a filter on another indexed column, such as `companies?created_by=eq.<account>`, can make the scan fetch the few rows that match it and drop them by that plain comparison, a matter of microseconds rather than a function call and a roster lookup for each.

PostgREST can also be set to hand back the plan of any request (its `db-plan-enabled` setting, off unless turned on). Keep it off in production: with it, `Rows Removed by Filter` in a plan counts rows the caller cannot see, such as another account's companies through that `created_by` index.

### A company always keeps a supervisor

Every company keeps at least one active supervisor whose account can still sign in, so someone can always let people in. An account counts while it is on the row and Supabase Auth has neither soft-deleted it (`deleted_at`) nor banned it (`banned_until` still to come). Whatever would take the last one away is refused, by a trigger on the roster as well as in the functions: a role change, taking the row off the roster, deleting it, releasing its claim, handing it to someone else, or deleting the supervisor's account. To step down, the last supervisor makes someone else a supervisor first. Deleting the whole company is allowed, and takes its roster, requests, notifications and holds with it.

A soft delete or a ban is a change to Supabase's own `auth.users`, which these migrations never put a trigger on, so the database cannot refuse it. And it is a Supabase Auth call, outside the database's transaction, so checking `is_last_supervisor(user_id)` and then banning does not hold when two such requests overlap: each check sees the other supervisor still there, and both bans go through. **The server steps an account down first, with `step_down_everywhere(user_id)`, and bans or soft-deletes it only once that has returned.** It makes the account an employee on every active supervisor row it holds, in one statement, so the guard refuses it (`23514`, nothing changed anywhere) while the account is the last supervisor who can sign in in any company; two at once for the supervisors of one company take turns, and the second is refused. `is_last_supervisor` stays, to show which accounts are the last supervisor somewhere. A hard delete (`auth.admin.deleteUser(id)`) is refused by the guard already: Supabase Auth's admin delete then answers 500 and passes the database's `23514` on in its body. A person deleting their own account goes through the `delete-account` function, which asks first (see [Deleting an account](#deleting-an-account)). Once an account is soft-deleted or banned it stops counting, so the other supervisors cannot step down past it, and it has no supervisor power left (see [Who can do what](#who-can-do-what)).

The guard holds even when two changes overlap. Before it counts, it writes a row (`company_supervisor_guard`) for each company that lost a counting supervisor in the statement, in a fixed order so two statements cannot deadlock. So two transactions that each remove a different supervisor of the same company — two supervisors stepping down at once, releasing each other, or one supervisor sending two requests — cannot both go through. At READ COMMITTED (PostgREST's default) the second waits, then sees the first's committed change and is refused (`23514`). At REPEATABLE READ or SERIALIZABLE, as a direct connection or a function may run, the second is told to try again (`40001`); when it does, it sees the first's change. A lock alone would not do at those levels: it makes no new row version, so the second would count with its older snapshot and both could commit, leaving the company with none.

## The functions

Write to MineMuster to start more."), which is the one given when both apply, since waiting a day does not lift it. A call refused for what was typed counts toward neither. When a function refuses, the error's code says why:

| Code | Means |
|---|---|
| `42501` | Not signed in, an anonymous sign-in where an account is needed, an account Supabase Auth has banned or soft-deleted, or a write the API does not allow ("permission denied"). |
| `22023` | Something typed is missing or not allowed: a blank name, a name with a control or invisible character or with letters of more than one alphabet, a name that only looks like one on the roster, a state that is not a postal code, an unknown time zone, a role that is not employee or supervisor, a logo path outside the company's own storage, a call to `push_records` whose changes are not a list or number more than 200, a contact form field that is missing or too long, an `apply_stripe_event` call with something that is not a Stripe event, or a company's name typed otherwise than it is to close it (`close_company`, hint `wrong_name`), a passcode the rule refuses (`crew_keep_passcode`; hint `not_digits`, `too_short`, `too_long` or `easy`) or something that is not an email address (`invite_supervisor`; hint `email_invalid`). |
| `PT404` | Not found, or not the caller's to act on. The two look the same on purpose: a missing roster row or invitation, and one of a company the caller does not supervise, give word for word the same answer (`supervisor-tools` answers it as 404 `not_found`). PostgREST answers it with HTTP 404. (Before migration `20261117000600` this was `P0002`, which PostgREST answers with 500.) |
| `PT409` | Not in a state to do that: a request already decided, a row already claimed or taken off, a person already on the roster, a company someone else can take over or whose subscription still runs (`close_company`, hints `someone_can_take_over` and `subscription_running`), and, for crew passcodes and invitations, a supervisor's row for a passcode account (hint `supervisor_needs_email`), a second company's row for one (`passcode_account_elsewhere`), a row no passcode account holds (`not_a_passcode_account`), a row taken off the roster or held by an email account (`row_taken`), an invitation that expired, was cancelled or accepted, or whose inviter is no longer a supervisor (`invitation_closed`), an account whose confirmed address is not the invited one (`wrong_email`) and one already on the company's roster (`already_on_roster`). PostgREST answers it with HTTP 409. (`55000` before `20261117000600`, also answered with 500.) |
| `PT402` | MineMuster is not active for the company: `read_shared_records` called by a supervisor of a company without it (see [What a supervisor reads](#what-a-supervisor-reads)). PostgREST answers it with HTTP 402. |
| `23514` | It would leave the company without an active supervisor. (Also a check constraint, such as a state that is not one of the 51, or a pay period over 16 KiB as text, over 64 KiB as stored, or holding a number no browser sends.) |
| `PT429` | A limit: the contact form's (too many messages from one email address, from one sender, or from everyone in the last hour), or `create_company`'s (3 companies started in any 24 hours, 20 in all, for one account). The hint says which. PostgREST answers it with HTTP 429. |
| `40001` | Two changes to the same company's supervisors overlapped at REPEATABLE READ or SERIALIZABLE. Try again. (PostgREST runs at READ COMMITTED, where the second waits and gets `23514` instead.) Also two `push_records` calls from one company at once, at those levels: the second has to try again. And the one 40001 `push_records` raises itself ("Another phone was sending the same record. Try again."): a record written by something other than `push_records`, as the owner can in the SQL editor, after `push_records` read and before it wrote. PostgREST tries a 40001 again by itself, with no limit; the call made again reads that record and is answered at once, as for any record already there (`record_races.db.mjs`). Nothing an API caller does can make it last: every write to `records` through the API is `push_records`, which takes the company's counter before it reads. |

PostgREST picks the HTTP status from the code: a `PTnnn` code is HTTP nnn, with its message and hint kept in the body; `42501` is 401 without a sign-in and 403 with one; `22023` and `23514` are 400. Every refusal is one of these, never a code PostgREST answers with 500 (`security.db.mjs` reads every raise in every function to check, whatever its shape: `raise sqlstate '...'`, a condition name such as `no_data_found`, the code in any case or spacing, an `assert`, and a handler raising again what it caught, each with the code PostgreSQL itself gives it); the `40001` above is not a refusal. A raise with no code of its own (`P0001`) would be 400 and a duplicate raised again (`23505`) 409. Read the code, not the status: PostgREST also answers 404 for a function that does not exist (`PGRST202`) and 409 for a duplicate (`23505`). A client should still read `P0002` and `55000` as these two, for a server where `20261117000600` has not run yet; the phone and the dashboard do. PostgREST writes a `PTnnn` code's message into the HTTP status line too (`HTTP/1.1 404 No such company.`), so such a message is always a constant on one line, never text from the request: a line break in it would start a header.

## Crew sign-in

A crew member gets into the app with their company's code, their first and last name and a passcode, and has no email (migration `20261122000100`). Supervisors keep signing in with email and a password. The wording the app shows for every answer is in `src/domain/serverAnswers.ts`.

- **A crew account is an ordinary Supabase Auth user that the server makes**, never the person: a hidden address `crew-<32 hex digits>@crew.minemuster.com`, on a domain MineMuster owns that receives no mail, and a long password the database works out from that address and a key of its own (`crew_login_password`: SHA-256 of the key, `login:` and the lower-case address, in base64). The user is made with its address confirmed and `app_metadata.sign_in` of `passcode`, which only the server writes. Nobody, the person included, ever sees the address or the password, and the app is never handed the address. A crew account is one with a `crew_logins` row; nothing in SQL decides anything from the address. Signing in is Supabase Auth's ordinary password grant, made by `crew-auth`, so a crew session is an ordinary session that the phone keeps and refreshes.
- **The key and the logins.** `crew_key` is a one-row table with a key the migration makes at random, so nobody ever sees it. `crew_logins` has a row for each crew account, which goes with the account: its salt and digest, its wrong tries in a row and its lock, a reset code kept the same way (`reset_digest`, `reset_until`, `reset_tries`), and when the account was made and its passcode last set. No API role, the server key included, reads or writes either, nor `crew_sign_in_tries`.
- **The passcode** is 6 to 12 digits and not an easy one. `crew_passcode_problem(passcode)` answers null, or `not_digits`, `too_short`, `too_long` or `easy`: one of the most common 6-digit passcodes in published PIN studies, a run up or down, one block of 2 digits or more repeated to fill it, three or more doubled digits counting up or down, or a palindrome (which takes in every digit the same). It is the same rule as `passcodeProblem` in `src/domain/passcode.ts`; `crew_passcodes.db.mjs` holds the two to the same answer over a few hundred strings, so change them together. A passcode is kept only as a digest, SHA-256 of the key, the account's own 16-byte salt and the passcode.
- **Wrong tries.** `crew_check_passcode(p_user, p_passcode)` reads the account's row for update before its counts, so guesses sent at once are counted one by one. 5 wrong in a row lock the account for 15 minutes and 10 lock it until a reset, the right passcode refused as well while it is locked (and then neither compared nor counted). A right passcode clears the count.
- **Reset codes.** A supervisor makes one on the dashboard's Roster page (Reset passcode: `make_passcode_reset_code`, for a row held by a passcode account) and is shown it once. It is 6 digits, from random bytes, good for 30 minutes and 5 tries, kept only as a digest, and a new one replaces the one before with all 5 tries again. It works while the account is locked and opens nothing by itself: the lock and the count stay until it is used. In the app, **Forgot your passcode?** takes the code and a new passcode (`crew_reset_check`): the new passcode is checked first, so one the rule refuses spends no try; a wrong code is counted and the fifth wrong one spends the code; the right one keeps the new passcode, which clears the count, the lock and the code. `crew-auth` then signs the account out of every other phone, so a lost or old phone stops working.
- **Delete sign-in.** `crew_sign_in_to_delete(p_roster_id)` gives a supervisor of the row's company the passcode account on it, and `supervisor-tools` deletes it with Supabase Auth's admin API: a hard delete, which ends every session. The row and every record stay with the company, the link to the account cleared (what the person's own deletion keeps, see [Deleting an account](#deleting-an-account)), and the person can sign up for the row again. This is also the fix when someone signs up under a coworker's name.
- **Only crew, and one company.** The roster's write trigger (`roster_before_write`) refuses (`PT409`) a supervisor's row to a passcode account (hint `supervisor_needs_email`) and a row in a second company (`passcode_account_elsewhere`), whatever writes the row: `approve_join_request`, a role change, an insert. `crew_keep_passcode` refuses the other way round, for an account that holds a supervisor's row, or rows in more than one company, rows taken off the roster included, so neither comes about the other way. Both take the account's lock first, so two writes for one account take turns: the trigger takes it for a write that puts an account on a row or makes a row an account holds a supervisor's, the only writes that change what keeping a passcode reads, and for no other, so a statement over many rows (a job title written over a whole roster) waits on no account. `crew_reset_check` takes the same lock before the account's `crew_logins` row, the order `crew_keep_passcode` takes them in.
- **Whom a name finds** (`crew_find_person`, in this order). The active rows `find_on_roster` gives for the name, as joining matches it: one row is the person (a supervisor's row, or a row an account that is not a crew account holds, is `use_email`; a row a crew account holds is that account; a row nobody holds is nobody's, unless a crew account's request waits under that name, as one does when a supervisor puts the name on the roster before letting the request in), and several rows are `ambiguous`. Else an inactive row with exactly that name held by a crew account: someone taken off the roster, who can still sign in, only to delete their account (row level security already keeps an account with no active row out of the company's records, and the app shows its off-the-roster screen). Else a pending join request with exactly that name left by a crew account. "Exactly" is as `same_name` reads a name, capitals and runs of spaces aside.
- **Too many tries from one place.** Each crew-auth request but `confirm` is counted by `crew_try_counted(p_address)`: at most 30 from one network address in 10 minutes. It keeps one row for each request let through in `crew_sign_in_tries`, holding only a digest of the address made with the crew key (never the address, so the rows cannot be turned back into addresses by trying every address) and the time. A request deletes every row older than 10 minutes, whoever it came from, when it gets the prune's own lock, one for every address, which a request tries for and never waits for: while one request is deleting, the others pass the old rows by and leave them to it, so two deletes never meet. A row is usually gone with the next request after its 10 minutes, and otherwise with the next one that gets the lock; the count reads only the last 10 minutes either way. A request turned away is not counted, so a crew behind one address on a training day does not keep itself waiting longer. Requests with no address all count as one sender, so sending none gets nobody past the limit. Requests from one address take turns, so two at once cannot both slip under it. `crew-auth` reads the address from `cf-connecting-ip`, else the first `X-Forwarded-For` entry. Signed-in lookups of a company code (`company_by_code`) are not limited, on purpose.

### The checks

`crew-auth` asks these with the server key, by POST (a check counts the request and a wrong try, and PostgREST runs a GET in a transaction that cannot write), before it talks to Supabase Auth. Each answers in jsonb and never raises, since `crew_check_passcode` counts a wrong try in the caller's transaction and a raise after it would roll the count back and give a guesser a free try. Each that takes the phone's address (`p_address`) counts the request first and answers `busy` when the limit is reached.

| Check | What it answers |
|---|---|
| `crew_lookup(p_code, p_address)` | `company` with `name` and `state`, `no_company` or `busy`. The code is read as joining reads it. |
| `crew_sign_up_check(p_code, p_first, p_last, p_passcode, p_address)` | Whether a sign-up may go ahead, making nothing. In the order it checks: `busy`, `no_company`, `easy_passcode` (with `problem`), `bad_name` (with `message`: a name `join_company` refuses for what it is), `already_signed_up` (a crew account has that name, or several signed up with it: sign in, or ask a supervisor for a reset code), `use_email` (a supervisor's row, or one an email account holds), `bad_name` again (a name that only looks like one on the roster), or `ok` with the hidden address and password to make the account with. |
| `crew_sign_in_check(p_code, p_first, p_last, p_passcode, p_address)` | `busy`, `no_company`, `ambiguous` (the name fits several people, or several crew accounts signed up with it; no passcode is checked, so no try is counted against anyone), `use_email`, `no_account`, `wrong` (with `tries_left`), `locked` (with `until`, or null until a reset), or `ok` with the login to sign in with, the company and `waiting` (true when a request that waits for a supervisor found the person). |
| `crew_reset_check(p_code, p_first, p_last, p_reset_code, p_new_passcode, p_address)` | `busy`, `no_company`, `ambiguous`, `use_email`, `no_account`, `easy_passcode`, `expired` (no code to try: none made, used already, past its 30 minutes or its 5 tries spent), `bad_reset_code` (with `tries_left`), or `ok` with the login. It works while the account is locked. |
| `crew_confirm_check(p_user, p_passcode)` | The passcode of the account signed in on the phone, before it is deleted: `wrong`, `locked`, `no_account` or `ok` with the login. It goes by the account, not by a code or a name (the phone keeps no code, and a supervisor can change the code or correct the name), and it is not counted against the address. |

### The crew-auth function

`functions/crew-auth` is `index.ts`, which starts it, and `handler.ts`, what it does, with `../_shared/server.ts` and `../_shared/http.ts`. It is for the app only, and reads the same settings as `delete-account` (the project's address and the server and publishable keys); nothing else is set.

1. A request with an `Origin` is a web page's and is 403 `origin_not_allowed` before anything is asked: the app sends none, so passcode sign-in is for iOS and Android, and the web build offers email. Any method but `POST` is 405.
2. The body is JSON, at most 4096 bytes (413 `too_large` when said to be larger or found larger while read, with no more of it read; any other is 400 `bad_request`), with an `action` and exactly its fields, all text: `lookup` (`code`); `sign_up` and `sign_in` (`code`, `first_name`, `last_name`, `passcode`); `reset` (`code`, `first_name`, `last_name`, `reset_code`, `new_passcode`); `confirm` (`passcode`, with the session signed in on the phone as the bearer token).
3. The network address is `cf-connecting-ip`, else the first `X-Forwarded-For` entry, and none when that is not an IPv4 or IPv6 address. The database counts every request but `confirm` against it, and answers `busy` past 30 in 10 minutes.
4. A refusal is answered 200 `{status, ...}` as the check gives it. `sign_up` makes the account (Supabase Auth's admin API, address confirmed so no mail is sent), keeps the passcode (`crew_keep_passcode`), signs in and calls `join_company` as the new account, with its own token, so every join rule applies unchanged: `joined`, `already_member` or a `pending` request. If anything fails once the account is made it is deleted again with Supabase Auth's admin delete, and the answer says why (the join's refusal: `no_company`, `denied`, `ambiguous` or `bad_name`; `already_signed_up` when another sign-up took the name meanwhile; `busy` for Supabase Auth's 429; or 500 `try_again`). `reset` signs in with the new passcode and then signs the account out everywhere else with the fresh session, tried twice: the session answered says `others_signed_out`, false when both failed (the app then does it itself), and from the kept passcode on nothing answers `busy` or `try_again`, which would have the person try a spent code (a sign-in that fails is 200 `passcode_changed`). `confirm` checks whose the bearer token is (401 `signed_out`, 410 `already_deleted`), then `crew_confirm_check`, then signs in again: a fresh session to delete the account with.
5. A sign-in is 200 `{status: 'signed_in', session: {access_token, refresh_token, expires_at, user_id}, company: {id, name}, waiting}`, with `join` on `sign_up`. Missing settings are 500 `not_set_up`, before anything is asked; anything else that fails is 500 `try_again`. The log says what happened as a code, never a name, a passcode, a reset code, a company code, an address, an email, a token, a key or an id.

**Deploying it.** JWT verification off: someone signing up or in has no token yet, and the function asks Supabase Auth about `confirm`'s token itself. With the CLI, from the repository root: `supabase functions deploy crew-auth --no-verify-jwt`. Through the Supabase MCP server or the dashboard: `crew-auth/index.ts`, `crew-auth/handler.ts`, `_shared/server.ts` and `_shared/http.ts`, with `verify_jwt` off. Apply `20261122000100` first: the function asks the database's checks, which that migration makes.

**Sessions.** Check under Authentication that Supabase Auth keeps sessions with no time limit and no inactivity timeout (its default): the app never signs anyone out by itself, and a time-boxed session would. Refresh-token reuse detection stays on, at its default reuse interval of 10 seconds. Weak signal does not sign a phone out through it: Supabase Auth takes a refresh token again, whatever the interval, when it is the one just before the session's current token, and answers with the current one (`internal/tokens/service.go` in Supabase Auth v2.198.0, the version the live project runs). So a phone that sent a refresh and lost the answer tries again with the token it kept and stays signed in. The interval only covers two refreshes sent at about the same time.

**Checks to make once it is deployed.** Both depend on the live project and on Supabase's edge, which no test here reaches:

- **The address that is counted.** `crew-auth` counts requests by `cf-connecting-ip`, else the first `X-Forwarded-For` entry. Send lookups with a made-up `cf-connecting-ip`, and then with a made-up `X-Forwarded-For`, through both addresses the function answers on (`https://<project-ref>.supabase.co/functions/v1/crew-auth` and `https://<project-ref>.functions.supabase.co/crew-auth`), and count the senders in `crew_sign_in_tries` (digests only). A caller who can choose the address that is counted gets past the limit of 30. If either header reaches the function as the caller sent it, count by the address the platform adds instead. Checked on the live project on 2026-11-23, through both addresses: Cloudflare turns away a request that carries its own `cf-connecting-ip` (403, error code 1000) before Supabase sees it, and sets `cf-connecting-ip` itself, equal to `x-real-ip`, on every request that reaches the function. A made-up `X-Forwarded-For` arrives as sent, but with `cf-connecting-ip` always there it is never read (the function's request logs, and one counted sender for each real address).
- **Supabase Auth's own limit.** Supabase Auth limits requests by the caller's address (Authentication, Rate Limits). A password sign-in is a `/token` request, and every `/token` request counts against the limit for token refreshes (`rate_limit_token_refresh`; `internal/api/apilimiter` in Supabase Auth v2.198.0). Every password grant `crew-auth` makes reaches Auth from the function's own address, so the crews of every company share that one limit, and past it crew sign-ups and sign-ins answer `busy`. Set it high enough for several crews signing in on the same morning: the live project's is 300 per 5 minutes. It also limits how fast one address can try passwords for email accounts.

### Known limits

Written down and accepted (the design is `docs/superpowers/specs/2026-11-22-crew-passcode-sign-in-design.md`):

- Anyone with the company code can try to sign up under a name not yet signed up. Supervisors see who has joined on the Roster page, fix a wrong one with Delete sign-in, and rotating the code stops people who have left.
- A coworker can try passcodes on one name. 10 wrong tries lock it until a reset, so the chance of a guess is about 10 in a million per account, with easy passcodes refused. The per-address limit slows trying many names. There is no company-wide slowdown, on purpose: it would let one person lock the whole crew out of signing in.
- Names written the same always answer `ambiguous` at sign-in.
- A removed crew account blocks a sign-up under its exact name (`already_signed_up`) until a supervisor deletes that sign-in or adds a row for the newcomer.
- An unheld active row with the exact name stops the search for the name (the person typing it is most likely the newcomer, who signs up), so a removed person in that corner asks a supervisor to delete the old sign-in.
- An invited address with no account, or one not confirmed, gets an unconfirmed Supabase Auth account made by the invite email (`POST /auth/v1/invite`), holding the address and `data.company_name`. It is not part of `supervisor_invitations`, does not cascade, and nothing removes it if the person never accepts. The person can delete it from the dashboard's Your account page once signed in, or through the contact form (see [Deleting an account](#deleting-an-account)); a later clean-up job could remove accounts like it that never confirmed.
- An admin create that times out may leave an unused hidden-address account with no passcode. It is harmless, since nothing can sign in to it. A later clean-up job could remove `crew.minemuster.com` users with no `crew_logins` row.
- A confirmed address skips the Auth call when invited, so its answer comes faster. A supervisor timing the answers could guess whether an address has an account.
- Signed-in lookups of a company code are not limited.
- If signing other phones out fails after a passcode reset, the phone warns and does not try again later.
- Two sign-ups for one name that is on no roster row, sent at the same moment from two phones, both pass `crew_sign_up_check` before either has joined, and both joins leave a request: two crew accounts and two requests stay. Sign-in then answers the name `ambiguous` until a supervisor lets one in and turns the other down. The app's own guard stops one phone sending a sign-up twice, so it takes two phones at once.
- An acceptance onto a row a passcode account holds, at the same moment as that passcode account is deleted (a supervisor's Delete sign-in, or the person deleting their own account), can deadlock. The acceptance holds the roster row, then writes the released hold, whose key takes a share lock on the account's `auth.users` row. Supabase Auth's admin delete locks that `auth.users` row, then its `on delete set null` waits for the roster row. One of the two ends in `40P01` and is undone whole: accepting can be tried again, and the deletion made again. Taking the company's row first in the acceptance does not cover this one.
- Records a deleted account sent stay with the company. A new sign-in for the same person cannot change a shift the old account opened (the server ties a record to the account that first sent it), so a supervisor closes such a shift with a correction, as before.

## Supervisor invitations

A supervisor invites another supervisor to the dashboard by email, from the Roster page (migration `20261122000200`). Nobody is put on the row until the invited person accepts.

- **The table.** `supervisor_invitations` has a row for each invitation: the company, the roster row, the address (trimmed and in lower case: `email_key`), who sent it (`invited_by`, cleared if that account is deleted) and when, until when it is good, and when it was accepted and by whom, or cancelled. No API role reads or writes it. Deleting a row deletes its invitations, and deleting a company reaches them through its rows.
- **Open invitations.** An invitation is open until it is accepted or cancelled. A row has at most one open one (a unique index): inviting again cancels the one before. It is good for 7 days (`expires_at`), and one past them is neither sent again nor accepted; inviting again replaces it. Nothing purges the table: an accepted, cancelled or expired invitation stays, address included, until its roster row or its company is deleted, which is what [the privacy policy](../site/privacy.html) says.
- **Whom it speaks for.** An invitation speaks with its inviter's authority: it is accepted only while the supervisor who sent it, or last sent it again, is still a supervisor of the company (`still_a_supervisor`: an active supervisor row held by an account Supabase Auth has neither soft-deleted nor banned). Sending it again vouches for it anew. `roster_sign_ins` says `invitation_lapsed` for one whose inviter no longer vouches, and the dashboard shows that it needs sending again.
- **The functions.** `invite_supervisor(p_roster_id, p_email)` is for a supervisor of the row's company, onto an active row that no email account holds (one nobody holds, or one a passcode account holds: a crew member made a supervisor). It answers `{invitation_id, email, company_name}`, the same whatever account the address belongs to, or none. `resend_supervisor_invitation(p_invitation_id)` gives an open, unexpired one 7 days more from now and answers `{email, company_name}`; `cancel_supervisor_invitation(p_invitation_id)` cancels one. `account_for_email(p_email)`, for the server key, says which account an address belongs to and whether it is confirmed (`user_id`, `confirmed`), so `supervisor-tools` asks Supabase Auth to send an invite email only to an address with no account or one not confirmed. `my_supervisor_invitations()` lists the open, unexpired invitations to the caller's confirmed address that accepting could still take. `accept_supervisor_invitation(p_invitation_id)` checks, in one step under the row's lock (taken after a share of the company's row, in `close_company`'s order, so the two take turns), that the caller's confirmed address is the invited one (`wrong_email`), that the invitation is still open, unexpired and its inviter still a supervisor (`invitation_closed`), that the caller holds no row of the company already (`already_on_roster`) and that the row is still on the roster and no email account holds it (`row_taken`); then it lets go of a passcode account on the row, with a released hold so it cannot take the row back by typing the name, makes the row a supervisor's and puts the caller's account on it. Accepting never lets go of an email account. The keep-a-supervisor guard counts nobody for the row until then.
- **Refusals** are as `release_roster_claim` gives them: `42501` only when nobody is signed in; `PT404` for a row or an invitation that is not there or is of a company the caller does not supervise, word for word the same either way (so a refusal never tells a real id from a made-up one; `roster_sign_ins` answers a company the caller does not supervise as `company_billing` does); `PT409`, with a hint, for one in a state that will not do; and `22023` with hint `email_invalid` for something that is not an email address (at most 254 characters once cleaned, no control or invisible character, a part of 1 to 64 characters before an `@` and a domain with a dot).
- **The roster's sign-ins.** `roster_sign_ins(p_company_id)`, for a supervisor, gives each row's `sign_in` (`none`, `passcode` or `email`), `locked_until` (while 5 wrong tries keep a passcode account locked), `needs_reset` (10 wrong tries), and the row's open, unexpired invitation: `invitation_id`, `invited_email`, `invited_at` and `invitation_lapsed`. It is the Account column of the Roster page.
- **Tests.** `tests/stand-ins.mjs` plays PostgREST's `/rest/v1/rpc/*` over a local database and Supabase Auth's routes for the two function test files, and `tests/supabase-stub.mjs` gives `auth.users` an `email_confirmed_at` column, set once Supabase Auth confirms an address (the migrations read it, never the address's text, to tell a confirmed account). The "names no account in any argument" test in `account_deletion.db.mjs` now reads input arguments only, not the columns a function that returns a table answers with, and allows `invite_supervisor`'s `p_email` beside the contact form's: it is the address an invitation goes to, names no account, and answers the same whether or not an account has it.

### The supervisor-tools function

`functions/supervisor-tools` is `index.ts`, `handler.ts` and the same two shared files. It is for the dashboard: on the Roster page a supervisor invites another by email, sends an invitation again, or deletes a crew member's passcode sign-in, each of which needs Supabase Auth's admin API and so the server key, which the browser never holds. Who may do what is the database's to say: its function runs as the supervisor with their own token, and only once it has said yes does this function call Supabase Auth.

1. `OPTIONS`, a browser's preflight, is 204 with CORS for `https://app.minemuster.com` alone. A request with any other `Origin` is 403 `origin_not_allowed`; one with no `Origin` is no web page's and goes on. Any other method but `POST` is 405.
2. No bearer token: 401 `signed_out`. The body is JSON, at most 16 KB (413 `too_large`; any other is 400 `bad_request`): `{action: 'invite', roster_id, email}`, `{action: 'resend', invitation_id}` or `{action: 'delete_crew_sign_in', roster_id}`, each id a uuid, and no other field.
3. Supabase Auth says whose the token is, as for `delete-account`: a reason of its own to say no is 401 `signed_out`, none (the gateway refusing the key) is 500 `not_set_up`, no answer is 500 `try_again`.
4. `invite` calls `invite_supervisor`, and `resend` calls `resend_supervisor_invitation`, as the supervisor. Then `account_for_email`, with the server key, says whether the address has an account and whether it is confirmed. Only for an address with no account, or one not confirmed, is Supabase Auth asked to send its invite email (`POST /auth/v1/invite` with the address as the database keeps it, `data: {company_name}` and `redirect_to` of `https://app.minemuster.com/?invited=1`). A confirmed account is never sent one: its invitation waits on the dashboard until it signs in. Either way, and whatever Auth answers, the answer is 200 `{status: 'sent'}`, so it never tells whether an address has an account; a failure is logged by its code, the invitation stays, and Send again sends it once more.
5. `delete_crew_sign_in` calls `crew_sign_in_to_delete` as the supervisor, then Supabase Auth's admin delete (a hard delete, which ends the account's sessions): 200 `{status: 'deleted'}`, also for an account Auth no longer has; any other answer, or none, is 500 `try_again`.
6. The database's refusals: `PT404` is 404 `not_found`, in the same words whether the row or invitation is not there or is of a company the caller does not supervise (there is no 403 `not_supervisor`); `PT409` is 409 with its hint as the error (`row_taken`, `invitation_closed`, `not_a_passcode_account`); `42501`, and a token PostgREST turns down, are 401 `signed_out`; `22023` is 400 `bad_request`; anything else is 500 `try_again`. Every answer but `sent`, `deleted` and a preflight's carries `error`, a code, and `message`, plain words. The log says what happened as a code, never an email, a name, a token, a key or an id.

**Deploying it.** JWT verification off, as `delete-account` is: a browser's preflight carries no token, and the function asks Supabase Auth about the token itself. With the CLI: `supabase functions deploy supervisor-tools --no-verify-jwt`. Through the Supabase MCP server or the dashboard: `supervisor-tools/index.ts`, `supervisor-tools/handler.ts`, `_shared/server.ts` and `_shared/http.ts`, with `verify_jwt` off. Apply `20261122000200` first. Supabase Auth must allow `https://app.minemuster.com/?invited=1` as a redirect, or it sends the invite link to the Site URL, without `invited=1`, where the dashboard does not take it as an invitation. With the Site URL `https://app.minemuster.com`, as on the live project, it is allowed already: Supabase Auth allows any address with the Site URL's scheme, host and port (`IsRedirectURLValid` in `internal/utilities/request.go`). A project whose Site URL is anywhere else adds it to its redirect URLs (Authentication, URL Configuration). Wording Supabase's invite email for MineMuster is an optional setting of the project.

**Confirm email stays on** (Authentication, Sign In / Providers, Email). An invitation goes to the account signed in with the invited address once Supabase Auth has confirmed that address. With confirmation off, Supabase Auth treats every address as confirmed the moment someone signs up with it. Someone who signed up with an address before a supervisor invited it could then accept that invitation without owning the address.

**The email link's own lifetime.** An invitation is good for 7 days, but the link in Supabase Auth's invite email runs out on the project's own setting for email links (Authentication, under the email provider), which can be far shorter. Check it when deploying, and weigh making it longer. The live project's is 24 hours (86,400 seconds); the same setting covers sign-up confirmation and password reset links. A person whose link has run out is sent a new one with Send again, and the dashboard says that, without saying how long a link lasts.

## The records

Step 2: what the crew's phones share. Everything a person does in the app is saved on their phone first and sent when the phone can reach the server (`changesToSend` and `sendWaiting` in `src/domain/sync.ts`, through `pushTransport` in `src/services/server.ts`). The server keeps the latest version of each record in `records` and every version it has taken in `record_history`, and takes them only through `push_records`. The migrations are `20261117000100` (the tables), `20261117000200` (who reads them, and `my_companies`), `20261117000300` (`push_records`), `20261117000400` (the pay period's size, checked the same safe way as a record's), `20261117000900` (who completes a maintenance request) and `20261120000100` (the phones read the company's settings, roster, fleet and area sheets: see [Reading records](#reading-records)).

Since `20261120000100` a phone also reads the company's settings, roster, fleet and area sheets (see [What the phones read](#what-the-phones-read-read_shared_records)); every other kind it only sends. So a phone can be behind: on those four until its next read, and on the rest for good, where it has not seen a supervisor's correction or a deletion. A build of the app from before phones read is behind on all of them. Several of the rules below exist so that such a phone cannot undo what it has not seen.

A record has a kind, one of the eleven the server keeps: `settings`, `employee`, `equipment`, `areaSheet`, `shift`, `denied`, `leave`, `inspection`, `opLog`, `exam`, `mrf` (`SYNC_KINDS` in `src/domain/sync.ts`). Its id is the phone's own id for it; the shared settings are the one record `settings:company`, and hold only `company`, `site`, `workweekStartsOn` and `allowSectionAllOk`. Its rev is the phone's version of it, a hash of the record (20 hex characters from the app), or `deleted` for a record taken off a phone. A phone connected to its company sends a unit or a sheet it added (from a supervisor's sign-in, once it has read the company's records to the end at least once) ahead of everything else, then the records it makes, and the rest of the settings, fleet and sheets once it has read the company's (`sortedChanges`); it never sends a person.

### records

| Column | What it is |
|---|---|
| `company_id`, `kind`, `id` | The record: its company, kind and id, which together are its key. The id is 1 to 120 characters with no control character. |
| `rev` | The version last taken, 1 to 64 characters, or `deleted`. |
| `data` | The record as the phone sent it: a JSON object of at most 1 MB as stored and 256 KB as text (see [Size](#size)). `{}` once it is deleted. |
| `deleted` | True once a supervisor has deleted it. The row stays, so a phone that reads it learns it is gone. |
| `version` | How many versions of it the server has taken: its newest `version` in `record_history`. |
| `seq` | The company's number for its latest version. Every version a company's phones send gets the next number, so a client pulls what changed by asking for `seq` greater than the last one it has (see [Pulling what changed](#pulling-what-changed)). |
| `created_by`, `updated_by` | The account that first sent it, and the one that sent its latest version. Cleared if that account is deleted. |
| `created_by_supervisor` | Whether that first account was a supervisor of the company when it sent it. What an account sent as a supervisor stays a supervisor's: made an employee later, the account no longer reads or changes it. |
| `created_at`, `updated_at` | When it was first and last taken, for showing. Not for pulling: every change of one call has the same `updated_at`, and a call that started first can commit last. |

### record_history

Every version the server has taken, one row each, never changed afterwards. A signed record is not rewritten: when one changes, its new version is added beside the old.

| Column | What it is |
|---|---|
| `company_id`, `kind`, `id` | The record. |
| `version` | 1 for the record's first version, then 2, 3 and on; with the record, the key. Counted per record rather than from one sequence for every company, so a number says nothing about how much other companies send. |
| `seq` | The company's number for this version, as on `records`. Counted per company for the same reason. Within a company it does tell a member how many versions were sent between two they can read, kinds they cannot read included. |
| `rev`, `base` | The version, and the one the sending phone last had confirmed (null for none). |
| `data` | The record as it was sent, or null for a deletion. |
| `deleted` | Whether this version is a deletion. |
| `by`, `at` | The account that sent it, and when the server took it. `by` is cleared if that account is deleted. |

A trigger refuses every change to a version and every removal through SQL, by anyone, and TRUNCATE too. Two things get through: deleting the company takes its records and their history with it, and deleting an account clears `by` (its foreign key does that, and only once the account is gone) and changes nothing else. Every version belongs to its record (a foreign key), so while its company stands, a record cannot be deleted either. The trigger stops mistakes and every write through the API, the server key's included; it does not stop the database's owner, who can disable or drop it, and the server key can still delete a whole company, history and all. An audit trail that must hold even against the owner has to be copied somewhere the owner cannot change. In PL/pgSQL write the column as `"by"`: a bare `by` reads as a keyword there.

Two more tables are `push_records`' own, and only the server key reads them: `record_counters`, each company's latest `seq`, and `record_usage`, how much each account has sent today.

### Sending records: push_records

`push_records(company_id, changes)` takes up to 200 changes, each `{key, kind, id, rev, base?, record}` as `changesToSend` makes it, and answers with the ones it took, the ones it set aside and, only when there are any, the ones it left for a later call:

```json
{
  "accepted": [{ "key": "mrf:m-17", "rev": "0f3c9a1b2d4e5f607182", "conflict": true }],
  "ignored": [
    { "key": "employee:e-4", "rev": "9a1b0f3c2d4e5f607182", "reason": "supervisor_only" },
    { "key": "equipment:t-14", "rev": "5f6071820f3c9a1b2d4e", "reason": "open_request", "floor": "out_of_service" }
  ],
  "deferred": [{ "key": "exam:x-9", "rev": "2d4e5f6071820f3c9a1b", "reason": "call_size" }]
}
```

The phone marks `accepted` as sent (`markSent`, `readPushAnswer`), and most of `ignored`: it stops sending those, and for an ignored one the server keeps what it had. Three sorts of answer in `ignored` it does not mark. Of the settings, the fleet and the area sheets, `superseded`, `copy` or `deleted` makes it read the company's records again and send what is still to send, at most twice more in a round. `open_request` puts the unit back at least at its `floor`. `supervisor_only`, `not_yours` or `signed` on any record, or `malformed`, `private` or `too_large` on one of the four kinds phones read, is held on the phone and listed on its More screen, and sent again only once the record changes or the phone's account is made a supervisor. A deferred change is in neither list, so the phone sends it again in its next round. The changes are taken in order, in one transaction. A call whose changes are not a list, or that has more than 200, is refused whole (`22023`). Anything else wrong with one change sets aside that change only, so one bad record never stops the rest of a phone's records:

1. **Shape** (`malformed`, with a `problem` naming the change and what is wrong, such as "Change 3 has a key that is not its kind and id."; or `unknown_kind`). A change that is not an object, a kind the server does not keep, a key that is not `kind:id`, an id or rev out of bounds, a base that is not a rev, a record that is not a JSON object (or not null for a deletion), settings with an id other than `company`, or a record holding a number no phone sends. The key and rev come back as sent when they are text, and as null when they are not.
2. **Twice in one call.** The same key with the same rev gets the same answer; with another rev it is set aside (`duplicate`). One call writes one version of a record.
3. **Size** (`too_large`): see [Size](#size).
4. **Private** (`private`), whoever sends it: a record with a field named `payRates`, `payRate`, `passwordHash`, `salt`, `rate` or `hourlyRate`, in any capitals and at any depth (`settings.company.payRates`, an employee's `pay.rate`), and settings with any field but the four shared ones.

   **The shape the phones read** (`malformed`, with a `problem`), whoever sends it, the office dashboard included (`20261120000100`): every phone reads the settings, the roster, the fleet and the area sheets, and passes over a row it cannot read, so the server keeps none (`shared_record_problem`; `readRecord` in `src/domain/receive.ts` is the phones' side, and both are held to `src/domain/__tests__/fixtures/sharedRecords.json`). The record's `id` is the change's (settings have none). A person has a first and last name that are not blank, a `role` of `employee` or `supervisor`, `active` true or false, and a `title` and `payrollId` that are text when they are there. A unit has a `unit`, `make` and `model` that are text, a `category` the app has, a `status` of `ready`, `defect` or `out_of_service`, a `meter` from 0 to 10,000,000 and a `meterUnit` of `hrs` or `mi`. An area sheet has a `title` that is not blank, at least one line, each with an `id` and a `label` that are text and no id twice, `active` true or false, and `single` true or false when it is there. The settings have a company with a name that is not blank and a state the app has, a `site` that is null or has a `name`, a `radiusM` above 0 and a latitude and longitude for its centre, each point of its `polygon` and its town's centre, a `workweekStartsOn` from 0 to 6, and `allowSectionAllOk` true or false. Of the company, the server checks only the name and the state; the pay schedule, the mine ID and the earning codes are the phones' and the dashboard's own save's to check.
5. **A supervisor's** (`supervisor_only`): the settings, the roster (`employee`), the area sheets, paid leave, any deletion, a new unit in the fleet, and a new maintenance request that is not open and unassigned the way the app makes one (`20261117000900`): its `status` is not `open`, it names who it is assigned to, it carries something completing it writes (`completedAt`, `completedBy`, `timeSpent`, `remarks`; null is the same as left out), or its `history` is not a list (left out and null are fine) or has an entry that is not `open` or names who it is assigned to.
6. **Bounds** (`deferred`, reason `call_size` or `daily_limit`). Once a call has taken 8 MB of records, or the caller's account has sent 20,000 versions or 64 MB of records today (UTC), that change and every one after it in the call wait. What the server already has is still answered, and the count starts again the next day. The limits are constants at the top of `push_records`; a company whose phones send more than that in a day (a big crew's first sync after months offline, say) finishes the next day.
7. **What the server has.** The record is locked, after the company's row in `record_counters`, so one company's calls take turns from there until they commit.
   - The server has this version already, or this is the caller's own latest change to the record sent again (the same rev and base: a batch retried after its answer was lost): accepted, and nothing is written. Matching rev and base, not rev alone, still lets a record come back to an earlier version of its own (ready, red tag, ready, red tag).
   - **A version name names one content** (`20261120000100`): a change to the settings, the roster, the fleet or an area sheet that names an earlier version of the record with other content is `malformed`. A phone matches the versions it has by their names, so a name must never stand for two records.
   - The record is deleted: only a supervisor brings it back (`deleted`). Bringing back a record by the same id, such as an area sheet whose id is its name, is a supervisor's. Of the settings, the roster, the fleet and the area sheets, a change made from a copy the phone had before the record was taken out (it names a base) is `deleted` from a supervisor too; one with no base, from a phone that took the deletion, brings it back.
   - A change with no base onto a record the server has is a copy, not an edit (`copy`): always for the settings, the roster, the fleet and the area sheets, which every phone of a build starts with, and for the other kinds whenever someone else wrote the server's version. A new phone's fleet therefore never resets a red tag. For a shift, punch, checklist, log, exam, request or leave entry that another account sent first, the reason is `taken` (the phone made a record under an id that is not free); for the caller's own that someone else has changed since, `superseded`.
   - **The settings, the roster, the fleet and the area sheets are written only on top of the version a change was made from**, from anyone, a deletion too (`superseded`, `20261120000100`). Every phone takes the company's version of these before it sends its own, and the dashboard reads a record again before it saves it, so a change made from an older version is stale: the server keeps the newer one, and the phone receives it.
   - A member's change made from a version other than the server's, when someone else wrote the server's (`superseded`). An employee's phone that has not seen a supervisor's correction, a deletion or a date fixed does not undo it: the server keeps the supervisor's version as current.
8. **What a member may change** in a record already on the server. A supervisor changes anything. A member, who never deletes:

   | Kind | A member may | Otherwise |
   |---|---|---|
   | `shift` | On their own, while it is open: clock out, add a lunch (it ends by itself) and a break, end a break. No time already on it moves, nothing is taken off, a correction (`edits`) is a supervisor's, and once clocked out it does not change. | `signed`; someone else's: `not_yours` |
   | `denied` | Nothing: a turned-down punch is kept as it was. | `signed` / `not_yours` |
   | `inspection` | On their own checklist: what they decided after a defect, once, and the request it was sent on (`decision`, `mrfId`). | `signed` / `not_yours` |
   | `exam` | On their own exam: a date fixed on a line, once (the first date stands), and the request a line was sent on (`fixed`, `mrfId`). | `signed` / `not_yours` |
   | `opLog` | Their own log until it is checked in, its start left as it was; another operator's open log, ended (`endAt` and `endMeter` added, nothing else), as a new operator taking the unit does. | `signed` / `not_yours` |
   | `mrf` | The work on a request not yet completed and assigned to someone: `status`, `remarks`, `timeSpent`, `completedBy`, `completedAt`, and `history` added to. Who it is assigned to and what it is about are a supervisor's, and so is an added `history` entry that names who it is assigned to. With nobody assigned (no `assignedTo`, or one that is not a name), the work is a supervisor's too, all of it: a member changes nothing on it, so does not start it, move it back to open, complete it, write what completing it writes or add to its `history` (`20261117000900`). With someone assigned, any member may still work it and complete it, with any name as `completedBy`: see [Whose a record is](#what-the-server-works-out-and-what-it-does-not-check-yet). | `supervisor_only` |
   | `equipment` | A unit's `status`, and its `meter`, never down. | `supervisor_only` |

   "Own" means the caller's account sent it first, as an employee.
   **A unit's floor** (`open_request`, `20261120000100`), whoever sends it, a new unit too: a unit's `status` is never better than the company's open maintenance requests on it, as the server holds them (`unit_status_floor`). An open request that red-tagged it (`taggedOut`) keeps it `out_of_service`; any other open request keeps it at `defect` at best. Raising it is always taken. The entry carries `floor`, the best status the unit may have now. The floor is read after the call's earlier changes, so a request completed earlier in the same call counts as completed: send a completed request ahead of the unit it lowers. Once phones receive the fleet, one write that took a red tag off would reach every phone; this keeps "Red tagged. Do not operate." on every phone while the request that put it there is open.
9. **Write.** The record is written and the version added to the history, each with the company's next `seq`. A change made from a version other than the one the server had (a supervisor's, a supervisor bringing a record back, or the caller's own on top of their own after a lost answer) is still written, and its accepted entry carries `"conflict": true`.

A deletion (`rev: "deleted"`, `record: null`) keeps the row, marked deleted and emptied, and adds the deletion to the history. A supervisor's deletion of a record the server never had writes nothing and is accepted. An employee's deletion gets `supervisor_only` whether or not the record is there, so a deletion tells nobody which ids exist; it also means a phone dropping old denied punches (the app keeps the last 200) never deletes them on the server.

The caller must be an active member of the company. An account that is not, a member taken off the roster and a company that does not exist all get the same `PT404` ("No such company.", HTTP 404). anon cannot call it at all.

Who may send what, in short:

| Kind | Sends a new one | Changes one already there | Deletes |
|---|---|---|---|
| `settings`, `employee`, `areaSheet`, `leave` | a supervisor | a supervisor | a supervisor |
| `equipment` | a supervisor | a supervisor; any member: status and equipment hours | a supervisor |
| `shift`, `denied`, `inspection`, `exam` | any member | a supervisor; the member who sent it, as the table above allows | a supervisor |
| `opLog` | any member | a supervisor; its operator until checked in; any member, to end it | a supervisor |
| `mrf` | a supervisor; any member, open and unassigned | a supervisor; any member: the work on one assigned to someone, until completed | a supervisor |

A client that writes records the way a phone does (the office dashboard, say) sends the rev it read as `base`. Without one, a change to a record someone else wrote is a copy and is set aside.

### Size

jsonb keeps a number such as `1e131071` in a few bytes, and its text is 131,072 characters: a record of a few thousand of them would take a gigabyte to write out. So a record's size is checked without writing it out first, in this order: at most 1 MB as stored, no number a phone never sends (`JSON.stringify` writes nothing past ±1.8e308, and nothing nearer zero than 5e-324; such a record is `malformed`), and only then at most 256 KB as JSON text (`too_large`). The tables' own check constraints do the same, and so does the pay period's (`20261117000400`: 64 KiB stored, the same numbers, 16 KiB as text). A company logo kept in the settings as an image data URL is the record likeliest to pass 256 KB; the server sets such settings aside rather than stopping the phone, so the app should keep the logo well under that before it sends.

### Reading records

Through the tables (`supabase.from('records').select()`), by row level security:

- A supervisor reads every record of the company and every version of each.
- Any member reads the records the crew works from, `settings`, `equipment`, `areaSheet`, `inspection`, `opLog`, `exam` and `mrf`, and every version of them. Not people (`employee`): since `20261120000100` a member gets the roster through `read_shared_records`, below, without payroll IDs.
- A member reads the `shift` and `denied` records their own account sent first as an employee, and every version of those, a supervisor's corrections included, and nobody else's. Paid leave is entered by a supervisor, so a member reads none, their own included.
- A supervisor reads the company's records only while the company has MineMuster (`company_has_access`); without it they read none, not even what the crew reads. What the crew reads does not depend on billing, and nobody's sending ever does. See [What a supervisor reads](#what-a-supervisor-reads).
- Nobody reads another company's records. anon reads nothing. The server key reads the four tables and writes none.

As every policy here does, the two compare a row's company with the caller's own companies (`member_company_ids()`, and `supervisor_company_ids()` for what a supervisor reads), worked out once per statement, and call no function on each row: a request reads no row of another company, and takes no longer for a company with more records. What a member may not read is filtered from their own company's rows only.

`my_companies()` lists the companies the caller belongs to, for the app and the office dashboard to pick one: `id`, `name`, `state`, the caller's `role` there, and `join_code` where they are a supervisor (null elsewhere; an employee can still read the code from `companies`, as before). It counts membership as `is_member` does, so an account Supabase Auth has banned or soft-deleted belongs to none.

### What the phones read: read_shared_records

`read_shared_records(company_id, after, max)` (`20261120000100`) is how a phone takes the company's settings, roster, fleet and area sheets: the rows `(kind, id, rev, seq, deleted, data)` of those four kinds with `seq` above `after`, in `seq` order, at most `max` (200 when it is null, never more than 500, at least 1). A deleted record comes too (`deleted` true, `rev` `deleted`, `data` empty), so a phone learns a unit was taken out. A person's `payrollId` is left out of the data for anyone but a supervisor of the company; the `rev` is still the server's, of the whole record.

- The caller must be an active member of the company: otherwise `PT404` ("No such company."), as `push_records` answers.
- A supervisor of a company that does not have MineMuster gets `PT402` ("MineMuster is not active for this company.", HTTP 402), so the phone says so rather than take nothing for being caught up. Its crew reads as before, as through the tables.
- A page shorter than `max` is not the end; only an empty page is. Keep the highest `seq` read, as below.

The phones' read goes through the index `records_shared_seq`, so a company with years of shifts and checklists reads the four kinds as quickly as a new one.

A phone reads it in each round of sending, after its own new records have gone and after it has read its account's own row of the `roster`, which says whether the account is still on the roster and with what role (`companyTransport` in `src/services/server.ts`, the round in `src/services/sync.ts`). It merges each page in the same write as the highest `seq` of the page, so a page cut off is read again. It asks for 200 rows to start, half as many after a page that had no answer in 30 seconds, and twice as many, up to 500, after a full page that came back within 5 seconds. A round starts no new page after a minute of reading, and leaves the rest to a round two seconds later. The first time a phone has read to an empty page with no settings from the company, and the company on the phone does not pass `checkCompany` (no name or state, say), it takes the company's own row instead (`companies`): the name, the state, and the pay period when it is one the app can use.

### Pulling what changed

Page by `seq`, never by `updated_at` or by offset:

```js
const { data } = await supabase
  .from('records')
  .select('*')
  .eq('company_id', companyId)
  .gt('seq', lastSeq)
  .order('seq')
  .limit(1000);
// then lastSeq = the last row's seq, and repeat until a page comes back short
```

A company's calls take turns on its `record_counters` row, held until each commits, so a version with a higher `seq` became visible after every lower one: a pull never misses a version that committed late, and a record changed between two pages comes back on a later page at its new `seq`. The same goes for `record_history`. Keep the highest `seq` read, not the time.

### What the server works out, and what it does not check yet

- **A date fixed through a request.** The app writes the date a condition was fixed onto the exam when the person assigned completes the request it was sent on, and the request's id onto the exam line or checklist it came from. The server takes those only from the exam's or checklist's own maker or a supervisor. The completed request holds the same facts (`examId`, `findingKey`, `inspectionId`, `completedAt`, `completedBy`, `remarks`), so a condition is fixed on the server when its exam line has `fixed`, or a completed `mrf` names that exam and line. The dashboard should read both.
- **A unit's status and hours.** A phone reads the fleet and merges each unit's status and reading with its own before it sends a change to one (`mergeRows` in `src/domain/receive.ts`), and the server writes a unit only on top of the version a change was made from, and never better than the company's open requests on it (above). Still, `equipment` holds only what has reached the server: a unit is tagged out while an `mrf` for it is open with `taggedOut`, and its latest equipment hours are in its latest `inspection` (`meter`) and `opLog` (`endMeter`). The dashboard should work those out rather than trust `equipment.status` and `meter` alone.
- **Whose a record is.** The server goes by the account that sent it, not by the person it is about: it does not check that a shift's `employeeId` is the sender's, that a request is worked by the person it is assigned to, or that "completed by" names that person. For a maintenance request it holds what it can tell without that (`20261117000900`): a member's new request is open and unassigned, a request nobody is assigned to is worked only by a supervisor (started, moved back, completed), and no member's history entry names who it is assigned to. A request assigned to someone is still worked and completed from any member's account, with any name as `completedBy`; the app does not allow that (`canWork` in `src/store/useStore.ts`). The two-way sync work, which links each server account to the app's employee id, closes it. A shift a supervisor enters for someone is the supervisor's: that person's account cannot change it and does not read it. Linking each account to the app's employee id would let the server check these.
- **A phone connected with a crew account.** What a phone sends is judged by the account it is connected with, not by who is signed in to the app, so a phone connected with an employee's account cannot send a supervisor's work. The app goes by the same account: on a phone connected with a crew account nobody has a supervisor's powers (`supervisorHere` in `src/domain/access.ts`), and since a phone is one person's, only the person the sign-in is for is signed in to the app there, so nobody assigns a request there, or starts or completes one nobody is assigned to. What the server does not take from the account all the same, such as work done while the account was a supervisor's, is held on the phone: not counted as sent, listed on More under Not taken by the company with why, and sent again once the record changes or the account is made a supervisor (`readPushAnswer`, `receiving.held`). Linking each account to the app's employee id is still the two-way sync work's.
- **Payroll ids.** Since `20261120000100` a member who is not a supervisor reads no `payrollId`: no `employee` record, and no version of one, through the tables, and none from `read_shared_records`, which leaves the field out for anyone but a supervisor. A phone whose account is not a supervisor's stores none it receives, and takes off any it had once it finds the account is crew or off the roster (`mergeRows` and `standingChange` in `src/domain/receive.ts`).
- **Removing a version.** Nothing removes one version, a leaked field or a person's data included, short of deleting the company. Who may redact an audit trail, and how that is recorded, is still to be decided.
- **Phones do not yet show** a `conflict` or a `deferred` list; `readPushAnswer` reads `accepted` and `ignored` only. Of `ignored`, a phone shows what it holds and a unit kept at its floor, and none of the other reasons.

## Billing

Step 3: what a company pays. MineMuster is $300 a month per company, the whole crew included, with a 14-day free trial. A supervisor starts the trial at a Stripe payment link from the office dashboard: the card is taken there, and Stripe charges it automatically when the trial ends, then every month until the company cancels in Stripe's billing portal. Cancelling stops the next charge, and the company keeps access to the end of the period already paid for. Prices are in US dollars. Stripe keeps the cards, the invoices and the charges; the server keeps only where each company's subscription stands, from what Stripe tells it. The migration is `20261117000500_billing.sql`.

Stripe tells the server through a webhook: the edge function `functions/stripe-webhook` checks that a request really is from Stripe and hands the event to `apply_stripe_event` with the server key (see [The webhook](#the-webhook)). The office dashboard asks `company_billing` where its company stands, and opens its supervisor pages by that answer.

The Stripe account is shared with another business, whose products and events reach the same webhook. Only MineMuster's events change anything:

- A **checkout** is MineMuster's when the checkout session carries the metadata `app` = `minemuster` (Stripe copies a payment link's metadata onto every session it makes) and its `client_reference_id` is the id of a company on this server. The dashboard puts the company's id there when it builds the trial link. That is what ties a subscription to a company.
- A **subscription event** is MineMuster's when the subscription carries the metadata `app` = `minemuster` (the payment link sets it on the subscriptions it makes), or when it is a subscription a MineMuster checkout already brought in.
- Anything else is recorded as seen (its id, type and why it changed nothing) and changes nothing. Nothing else about another business is kept.
- So is every event from Stripe's **test mode** (`livemode` not `true`), whatever it is: a checkout paid with a test card never opens a real company. Test the integration against another Supabase project.

### billing_subscriptions

One row for each MineMuster subscription in Stripe.

| Column | What it is |
|---|---|
| `subscription_id` | Stripe's id for it (`sub_...`). The key. |
| `company_id` | The company its checkout named. Null until that checkout is seen, since Stripe can send the subscription's own events first. Set once: the first link stands. Deleting the company deletes its rows. |
| `customer_id` | Stripe's customer (`cus_...`). |
| `status` | Stripe's status: `trialing`, `active`, `past_due`, `canceled`, `unpaid`, `paused`, `incomplete` or `incomplete_expired`. Null while only the checkout has been seen. |
| `trial_end`, `current_period_end` | When the trial ends (and the first charge is made), and when the period already paid for ends. |
| `cancel_at_period_end` | The company has cancelled: nothing more is charged, and the subscription ends at `current_period_end`. |
| `event_at` | Stripe's `created` time of the newest event applied to the status. |
| `created_at`, `updated_at` | When the row was made and last changed. |

### billing_overrides

A company the owner lets in without paying: a pilot, a friend of the business, a company whose card trouble is being sorted out. One row per company: `reason` (1 to 500 characters, required), `until` (null for good), `created_at`. The company's supervisors can read the row, reason included, so write the reason for them to see.

### stripe_events

Every event the webhook has handed over, MineMuster's or not: `id` (`evt_...`), `type`, `outcome` (`applied`, or why it changed nothing) and `received_at`. An event Stripe delivers twice is applied once. No API role reads it, the server key included. The owner can read it in the table editor to see what Stripe sent and what was done with it.

### Stripe's events

`apply_stripe_event(p_event)` takes one event, already checked against Stripe's signature, and answers what it did:

| Event | What it does |
|---|---|
| `checkout.session.completed` | With `mode` = `subscription`, the MineMuster metadata and a `client_reference_id` that is a company here: ties `data.object.subscription` to that company (making the row if the subscription's own events have not yet). A subscription already tied to another company stays with it. |
| `customer.subscription.created`, `.updated`, `.deleted` | For a MineMuster subscription: sets its status, trial end, period end (`current_period_end` on the subscription in older Stripe API versions, on its first item in newer ones), `cancel_at_period_end` and customer, unless the event is older than the one the subscription is at. |
| anything else | Nothing. |

Its answer is `{applied: true, type, subscription_id, ...}` when it changed a subscription, or `{applied: false, reason}`:

| Reason | Means |
|---|---|
| `duplicate` | The event was handed over before. |
| `test_mode` | An event from Stripe's test mode (`livemode` is not `true`). Set aside before anything in it is read. |
| `ignored_type` | Not a kind of event MineMuster uses. |
| `not_minemuster` | Another business's checkout or subscription. |
| `not_subscription` | A MineMuster checkout that is not for a subscription. |
| `no_company` | A MineMuster checkout whose `client_reference_id` is not a company here. Tie it by hand (below). |
| `no_subscription` | The event names no subscription. |
| `already_linked` | The subscription is already another company's. |
| `unknown_status` | A status this migration does not know. Nothing changes; a new migration should learn it. |
| `no_time` | A subscription event with no `created` time. |
| `stale` | Older than the event the subscription is at. Stripe does not promise to send events in order. |
| `ended` | The subscription has ended in Stripe (`canceled`, `incomplete_expired`), which never starts again; only another ending is taken. |

It raises (`22023`) only for something that is not a Stripe event at all (not an object, or no id or type), and never for another business's event, so the webhook answers Stripe 200 and Stripe stops sending it. Times arrive as Unix seconds; one that is not a number between 1970 and the year 3000 is taken as none. Each event runs in one transaction, so a failure leaves nothing half done and Stripe's retry starts clean. Two deliveries of one event at once take turns, and the second finds the first; two events for one subscription at once take turns on its row, and the newer one stands (`billing_races.db.mjs`).

### Where a company stands

`company_billing(p_company_id)` is for the company's supervisors (an account Supabase Auth has banned or soft-deleted is none); anyone else is told there is no such company (`PT404`, HTTP 404), as by every supervisor function. It answers:

```json
{ "access": "trial", "status": "trialing", "trial_end": "2026-12-01T17:00:00+00:00", "current_period_end": "2026-12-01T17:00:00+00:00", "cancel_at_period_end": false, "running": 1, "had_trial": true }
```

| `access` | When |
|---|---|
| `comped` | The company has a `billing_overrides` row with no `until`, or one still to come. |
| `active` | A subscription is paid up. |
| `past_due` | A charge failed and Stripe is trying the card again. Still let in. |
| `trial` | The company's first free trial is running; or a checkout was done in the last hour and its subscription's own status has not come in yet. Checkout completes only once the card is taken, and the next event sets the real status, usually within seconds. |
| `ended` | Every subscription has ended (`canceled`, `unpaid`, `paused`, `incomplete` or `incomplete_expired`), or the only one still running is a second free trial. |
| `none` | No subscription, or only a checkout whose subscription never said its status (after that hour). |

**One free trial for each company.** A `trialing` subscription counts only when no other subscription of the company that had a trial was made before it. So starting a trial, cancelling it and starting another gives no second 14 days: the second shows as `ended` with status `trialing`, and opens the dashboard once Stripe charges it at the end of that trial. A company that has had its trial starts again on a payment link with no trial (the dashboard's `RESTART_LINK`, which charges the card at checkout). Two trials started at once (two supervisors, two tabs) count once.

**The subscription it goes by**, whose `status` and dates it gives (when the company is comped too), is the first of: one that is `active`, one that is `past_due`, the first trial, a checkout of the last hour, a second trial; and only when there is none of those, the newest (by `event_at`, then `updated_at`). So a company with a running subscription is never shut out by one that ended, such as a second checkout made by mistake and cancelled, and a checkout someone else made with the company's id (a payment link opened with it) cannot change what a paying company is told.

`running` is how many of the company's subscriptions Stripe will charge again: `trialing`, `active` or `past_due` and not cancelled, and a checkout of the last hour. More than one means the company is charged more than once a month; the dashboard says so. `had_trial` is true when a subscription of the company has had a free trial, the one it goes by included, so a new checkout would get no trial that counts.

The dashboard opens its supervisor pages on `trial`, `active`, `past_due` and `comped`, loads the records only then, and lets the supervisor in without an answer only when the server has no `company_billing` at all (`dashboard/src/lib/billing.ts`). To look for a company charged twice by hand:

```sql
select company_id, count(*) from public.billing_subscriptions
where status in ('trialing', 'active', 'past_due') and not cancel_at_period_end
group by company_id having count(*) > 1;
```

### What a supervisor reads

What a company pays for is checked on the server, where the dashboard's own code cannot skip it. `company_has_access(company_id)` is true for `comped`, `trial`, `active` and `past_due` (it is `company_billing`'s answer, through `billing_standing`, which no API role calls). A restrictive policy on `records` and on `record_history` (`records_select_paid`, `record_history_select_paid`) lets a row be read only from the caller's `records_open_company_ids()`: every company they belong to, but one they supervise only while it has MineMuster. Like every policy here, it compares the row's company with an array worked out once per statement and calls no function on the row. The array is worked out in one pass over the caller's roster rows (migration `20261117000700`): a company where the caller is a member and either not a supervisor or the company has MineMuster. Before, it asked `supervisor_company_ids()` again for each of the caller's companies, so its cost grew with the square of their number, and an account in about 1,400 companies took a call past the 8 s statement timeout. `membership_reads.db.mjs` holds it, and the other membership functions, to the answers of the definitions they replaced, case by case, and an account in 1,000 companies to well inside the timeout.

- A supervisor of a company without MineMuster reads none of its records, through the table or PostgREST, and `read_shared_records` answers them `PT402`, so their phone says MineMuster has stopped rather than take nothing for being caught up. They still read the company, its roster, its join requests and its billing, so the Billing page works.
- Sending is never stopped: `push_records` does not look at billing, so a phone never loses a safety record, and they are all there once the company is let in again.
- What a member who is not a supervisor reads is unchanged, and so is what their phone receives: `read_shared_records` goes by the same `records_open_company_ids`. Whether the crew's reads should stop too is the owner's call. A change to `records_open_company_ids` alone would stop both, but `read_shared_records` answers `PT402` to a supervisor only: a crew phone would get empty pages, which it takes for being caught up.
- There is no "billing not set up" exception on the server: billing arrives with this same migration, so wherever `company_has_access` exists, so does billing. A company that already uses the dashboard when this migration is applied reads its records again once it starts its trial, or once the owner adds its `billing_overrides` row (below), which is best done in the same sitting.

### Letting a company in without paying

In the SQL editor, which runs as the owner. Find the company's id first:

```sql
select id, name, state, created_at from public.companies order by name;
```

Let it in until a date, or for good with `until` left null:

```sql
insert into public.billing_overrides (company_id, reason, until)
values ('<company id>', 'Pilot through the spring', '2027-04-01')
on conflict (company_id) do update set reason = excluded.reason, until = excluded.until;
```

End it early with `delete from public.billing_overrides where company_id = '<company id>';`. Once `until` has passed, the row counts for nothing and the company goes by its subscription again.

A checkout that came in with no company (`no_company` in `stripe_events`, say a payment link opened without the dashboard) can be tied by hand once you know whose it is, from the customer in Stripe:

```sql
update public.billing_subscriptions set company_id = '<company id>'
where subscription_id = '<sub_...>' and company_id is null;
```

### The webhook

`functions/stripe-webhook` is a Supabase edge function (Deno), in three files: `index.ts` starts it, `handler.ts` is what it does, and `verify.ts` checks Stripe's signature. They use nothing but Web Crypto and `fetch`: no Stripe SDK and no supabase-js.

1. It takes `POST` only (405 otherwise).
2. It reads the `Stripe-Signature` header and checks its time before anything else, so a request that is not from Stripe costs no call to the database: 400 for a header that is missing, is not one Stripe sends, or was signed more than 300 seconds from now either way.
3. The signing secret is the function's `STRIPE_WEBHOOK_SECRET` when that is set, or else what `stripe_webhook_secret()` reads from Supabase Vault, kept for a minute.
4. It checks the signature as Stripe documents it: each `v1` is the HMAC-SHA256 in hex of `t.body` (the raw bytes Stripe sent), any `v1` may match, compared in constant time. 400 when none does.
5. It sends the event to `apply_stripe_event` through PostgREST with the server key, and answers Stripe 200 with what that answered, for an event set aside as well, so Stripe stops sending it. When the database cannot take the event (it cannot be reached, refuses the key, or does not have the function yet) it answers 500, and Stripe sends the event again later, for up to three days.

The server key is the `default` entry of `SUPABASE_SECRET_KEYS` (an `sb_secret_...` key, sent as `apikey` only, as Supabase asks), or else the legacy `SUPABASE_SERVICE_ROLE_KEY` (a JWT, sent as `apikey` and as the bearer token). Supabase sets both for its edge functions (Edge Functions, Secrets lists them). The log says what failed and never a secret, a key or an event's body.

**Where the signing secret lives.** In Supabase Vault, under the name `stripe_webhook_secret`, which keeps it encrypted in the database and out of the repository. The owner adds it once, in the SQL editor (or on the dashboard's Vault page):

```sql
select vault.create_secret('<whsec_... from the Stripe webhook endpoint>', 'stripe_webhook_secret', 'Signs the Stripe events MineMuster takes');
```

Only `stripe_webhook_secret()` reads it, and only the server key may call that. An edge function secret named `STRIPE_WEBHOOK_SECRET` (Edge Functions, Secrets) works as well and comes first when both are set. To roll the secret in Stripe, keep the old one valid for a while, put the new one in Vault (`select vault.update_secret(id, '<new whsec_...>') from vault.secrets where name = 'stripe_webhook_secret';`) or in the function's secret, and the webhook takes it within a minute. Never put a signing secret, a Stripe key or a server key in the repository.

**Deploying it.** JWT verification has to be off, because Stripe sends no Supabase token; the signature is the check. With the CLI, from the repository root: `supabase functions deploy stripe-webhook --no-verify-jwt`. Through the Supabase MCP server or the dashboard, deploy the three files `index.ts`, `handler.ts` and `verify.ts`, and `../_shared/server.ts`, which `handler.ts` imports the project's address and keys from (since `20261120000200`), with `verify_jwt` off. A copy already deployed with its own key code keeps working until it is deployed again. In Stripe, add a webhook endpoint at `https://<project-ref>.supabase.co/functions/v1/stripe-webhook` for these events only: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated` and `customer.subscription.deleted`. Its signing secret is the one to keep in Vault.

**What to check once.** That both payment links (the 14-day trial, and the one with no trial for a company starting again) carry the metadata `app` = `minemuster` and put the same metadata on the subscriptions they make (Stripe's payment link "subscription data"). Without it on the subscription, a subscription event that arrives before its checkout is set aside for good as `not_minemuster`, its cancellation included. Then that a live checkout shows up in `stripe_events` with the outcome `applied` and in `billing_subscriptions` with its company (cancel it in the portal afterwards). An event from Stripe's test mode only ever shows `test_mode` here, so a test card cannot show the whole path; test that against another Supabase project.

`npx tsc -p supabase/functions` type checks the function as Deno runs it (`functions/tsconfig.json`). The app's own `npm run typecheck` leaves `supabase/functions` out, because the files import each other with their `.ts` extension, as Deno needs.

## The contact form

The contact form on minemuster.com sends what a visitor typed to `submit_contact_request(p_name, p_company, p_email, p_phone, p_message, p_website)`, with the publishable key and nobody signed in (`POST /rest/v1/rpc/submit_contact_request` with the six as a JSON object). It answers `{ok: true}`.

- `p_website` is a field people never see. A form that fills it in is a bot: it is answered `{ok: true}` and nothing is kept.
- A field far over its limit is turned back before anything else is done with it (a name over 1,000 bytes, an email over 1,500, a message over 20,000, a company over 1,000, a phone number over 500), with the hint of that limit. Cleaning costs time for each character, and a refused call counts toward no limit, so a huge request costs the database next to nothing.
- Each field is trimmed and cleaned of control characters and of characters that show nothing: the same default-ignorable and format characters a name on the roster may not hold (zero-width spaces and joiners, direction marks, overrides and isolates, the soft hyphen, variation selectors, the Hangul and braille fillers, tag characters and the like). The message keeps its line breaks and tabs; the other fields are one line each, with runs of spaces closed up.
- Then it is checked. A name of 1 to 120 characters, an email address that looks like one (a part before the `@`, a domain with a dot, at most 254 characters), a message of 1 to 4,000 characters, and a company of at most 160 and a phone number of at most 40, both optional.
- The limits, so that one sender cannot shut the form for everyone and the table cannot be flooded: at most 3 messages from one email address (whatever its capitals) in 24 hours; at most 5 from one sender in an hour, the sender being the network address the request came from (the first entry of `X-Forwarded-For`, as Supabase documents the client's address); and at most 100 from everyone in an hour, a backstop for storage alone. Calls take turns from the counting to the commit, so two at once cannot both slip under a limit (at READ COMMITTED, as PostgREST runs).
- The sender's address is never kept. `contact_senders` holds a hash of it made with a key of this server's own (`contact_sender_key`, made at random by the migration), so the hashes cannot be turned back into addresses by trying them all, and each row is deleted by the next message once it is an hour old. A call with no such header (the SQL editor, say) counts only toward the other two limits.

When it turns a message back, the error's code and hint say why, and its message can be shown as it is:

| Code | Hint | Message |
|---|---|---|
| `22023` | `name_missing` | Type your name. |
| `22023` | `name_too_long` | Keep your name to 120 characters. |
| `22023` | `email_invalid` | Type an email address we can write back to. |
| `22023` | `message_missing` | Type a message. |
| `22023` | `message_too_long` | Keep the message to 4,000 characters. |
| `22023` | `company_too_long` | Keep the company name to 160 characters. |
| `22023` | `phone_too_long` | Keep the phone number to 40 characters. |
| `PT429` (HTTP 429) | `too_many` | Too many messages. Try again later. |

**Reading them.** What it keeps is in `contact_requests` (`name`, `company`, `email`, `phone`, `message`, `created_at`, `handled`). No API role reads it but the server key, so no visitor reads anyone's message, their own included. The owner reads it in the dashboard's table editor, or in the SQL editor:

```sql
select created_at, name, company, email, phone, message
from public.contact_requests where not handled order by created_at;

update public.contact_requests set handled = true where id = '<id>';
```

Nothing tells the owner when a message arrives; check the table, or add a notification later. What is left: a script that writes a new `X-Forwarded-For` into each request, if Supabase's gateway passes the first entry on as the client sent it, counts as a new sender each time, and so could still fill the 100-an-hour backstop and hold off real messages for that hour. A challenge on the form (Cloudflare Turnstile, checked by a small edge function before the insert) closes that; it needs the site as well as the server. The website's privacy page should say that the server counts messages by the address they came from, keeping only a scrambled form of it for an hour.

## Deleting an account

A person deletes their own MineMuster sign-in in the app (More, then Delete my account; or, from the company sign-in screen, Delete my account for a sign-in taken off the roster, or Delete this sign-in for an email sign-in on no company's roster), or on the office dashboard once its Your account page is built. A crew member's sign-in has no password, so the app asks for their passcode again: `crew-auth`'s `confirm` checks it against the account signed in on the phone and answers a fresh session, made with the account's own password, and the call to `delete-account` is the same from there (see [Crew sign-in](#crew-sign-in)). A supervisor can also delete a crew member's sign-in on the dashboard's Roster page (Delete sign-in, through `supervisor-tools`), which needs no password or email of the person's. It is a hard delete of the Supabase Auth account, made by the edge function `functions/delete-account` with the server key, and it cannot be undone. Migration `20261120000200` adds the two functions it asks first. Apple (5.1.1(v)) and Google Play ask for the account to be deleted, not frozen, from inside the app, and Google for a web page too: minemuster.com/delete-account.

**What goes**, by the foreign keys already in place: the `auth.users` row (the email, the password, the sessions and identities), the account's join requests with their notifications, its join holds and its send counts (`record_usage`).

**What stays**, as the company's: the person's roster rows, unclaimed (`user_id` and `claimed_at` cleared; a new account can claim the row again), and every record and every version they sent, with `records.created_by` and `updated_by` and `record_history.by` cleared, as are `companies.created_by` and `join_requests.decided_by`. The records are the company's, and the law has a mine keep some of them: its pre shift exam records for at least a year (30 CFR 56.18002(d)). An access token the deleted account still holds has no powers: every membership function joins `auth.users`, so `my_companies` comes back empty, and `push_records` and `read_shared_records` answer `PT404`.

**A company always keeps a supervisor.** The guard refuses the hard delete of the last supervisor who can sign in (see [A company always keeps a supervisor](#a-company-always-keeps-a-supervisor)). So that person first makes someone else a supervisor, on the dashboard's Roster page, or, when nobody else could take over, closes the company.

**Closing is never a way around handing over.** Any one supervisor can take every other row off the roster, delete it, or release its claim, so who could take over is more than who is active now. `close_company` waits while anyone else could still take over or come back (`closing_waits_until`): another row of the company holds an account that can still sign in (neither banned nor soft-deleted) and is active or was taken off in the last 30 days (`inactive_since`); or such an account was released from a row, or had its row deleted, in the last 30 days (a `released` join hold, which only approving that account's own request removes). So one supervisor acting alone cannot close a company others still use: the people taken off have 30 days to notice and ask MineMuster to stop it, and a supervisor whose crew has truly gone can close it once they have been gone 30 days. It also needs the password typed in the last ten minutes, by the token's `amr` (`password_typed_lately`), as the function does: a token left on a lost phone or in an open browser closes nothing, even called straight through PostgREST.

### account_deletion_check and close_company

| Function | Who | Gives back |
|---|---|---|
| `account_deletion_check()` | signed in | For each company the caller is an active member of, by name: `id`, `name`, the caller's `role`, `last_supervisor` (the only supervisor there whose account can sign in, as the guard counts them: the admin delete is refused exactly then), `successors` (told to a supervisor only: the other active rows whose account can sign in, as `roster_id`, `first_name`, `last_name`), `can_close` (a supervisor may close it now: nobody else could take over or come back; false for an employee), `close_from` (when only people taken off or released in the last 30 days stand in the way, the time from which it may be closed; else null) and `running` (told to a supervisor only: how many subscriptions Stripe still charges, as `company_billing` counts them; null for an employee). A banned or soft-deleted account gets `[]`. |
| `close_company(p_company_id, p_company_name)` | a supervisor of the company, with its name typed as it is and their password typed in the last ten minutes | Nothing. The company is deleted, and with it its roster, requests, notifications, holds, guard row, records and their history, counters and billing rows, by the cascade above. No account is deleted. |

Neither takes an account id: each answers for the signed-in caller only. `close_company` holds the company's row and its roster rows from its checks to the commit, so no claim, release or role change slips in between, and refuses:

| Code | Hint | When |
|---|---|---|
| `42501` | `password_needed` | The token's `amr` has no password sign-in in the last ten minutes. Asked before anything else, so such a token learns nothing about the company. |
| `PT404` | | Not a supervisor of that company, or no such company: the same answer. |
| `22023` | `wrong_name` | The name typed is not the company's, capitals and spacing aside. |
| `PT409` | `someone_can_take_over` | Someone else could take over or come back: an active row with an account that can sign in (make them a supervisor instead), or one taken off or released in the last 30 days (`close_from` says from when). |
| `PT409` | `subscription_running` | Stripe still charges a subscription of the company: cancel it first, in Manage billing. |

### The delete-account function

`functions/delete-account` is `index.ts`, which starts it, and `handler.ts`, what it does, with `../_shared/server.ts`, which reads the project's address and keys for it and for the stripe-webhook, and `../_shared/http.ts`, which reads its body and makes its calls. It uses nothing but `fetch`.

1. `OPTIONS`, a browser's preflight, is answered 204 with CORS for `https://app.minemuster.com` alone. A request with any other `Origin` is 403 `origin_not_allowed`, before anything is asked; a phone sends none. Any other method but `POST` is 405.
2. No `Authorization: Bearer` token: 401 `signed_out`.
3. The body is `{}` or `{"close": [{"company_id": ..., "name": ...}]}`, at most 20 companies and 16 KB. A body said to be larger (`Content-Length`) is 413 `too_large` with none of it read, and one found larger while it is read is 413 with no more of it read. Any other key, an account's `user_id` or `email` included, is 400 `bad_request`. Who is deleted never comes from the body.
4. Supabase Auth says whose the token is (`GET /auth/v1/user`, with the publishable key), and its own reason decides the answer when it says no. `user_not_found` (403, given only once it has checked the token's signature) is 410 `already_deleted`: the account was deleted from somewhere else. Any other reason of its own (`no_authorization`, `bad_jwt`, `session_not_found`) is 401 `signed_out`. A 401 or 403 with no `error_code` of Auth's, such as the gateway refusing the key, is 500 `not_set_up`: a setup problem, never a deletion.
5. **The password was typed in the last ten minutes.** The token's `amr` claim must hold `{"method": "password", "timestamp": t}` with `t` at most 600 seconds ago, or the answer is 403 `password_needed`. This was checked on the private local scan stack (Supabase Auth v2.198.0, 20 November 2026): a password sign-in gives `amr: [{"method": "password", "timestamp": <the sign-in's iat>}]`; a refresh keeps that timestamp while `iat` moves on; a new password sign-in starts a new session with a new timestamp. So the app signs in with the password just before it calls (`deleteAccount` in `src/services/server.ts`), and the dashboard's page must too. A custom access token hook that wrote `amr` as plain strings would make every deletion answer `password_needed`: keep the default claims, or change this step.
6. `account_deletion_check`, with the person's own token. A company they would leave without a supervisor, and are not closing, is 409 `last_supervisor`, with `companies: [{id, name, successors, can_close, close_from, running}]`. A company they ask to close has to be one they may close now (`can_close`) with nothing charged; otherwise 409 `close_refused` (with `close_from` when there is one), before anything is closed.
7. `close_company`, with their own token, for each company asked. A refusal is 409 `close_refused`, with `reason` (`wrong_name`, `someone_can_take_over`, `subscription_running` or `not_found`), `company_id`, and `closed`, the companies closed before it; its `password_needed` is 403 `password_needed`.
8. `DELETE /auth/v1/admin/users/{id}` with the server key and `{"should_soft_delete": false}`: a hard delete, given 15 seconds. A 404, an account deleted a moment before from elsewhere, counts as deleted. When it does not say it went through, Supabase Auth is asked again whose the token is: an account it no longer has was deleted all the same (200). When Auth answered the delete and turned it down, nothing was deleted: the last supervisor somewhere now (someone stepped down meanwhile, and the guard refused the delete) is 409 `last_supervisor`, anything else 500 `try_again`, with `closed`. When the delete got no answer, or only a gateway's (502, 503, 504), it may still go through: 504 `not_known`, with `closed`. The phone then asks Supabase Auth itself before it says anything, and never says nothing was deleted when nobody can tell.
9. 200 `{"deleted": true, "closed": [...]}`.

Missing settings are 500 `not_set_up`, before anything is asked; Supabase Auth or the database out of reach before anything was deleted is 500 `try_again`. Every answer carries `error`, a code, and `message`, plain words; the app puts it in its own words (`deletionAnswerWords` in `src/domain/serverAnswers.ts`). The log says what happened as a code (`delete-account: deleted`, `delete-account: password_needed`, ...), never a token, a key, an email or an id.

**Its settings.** Supabase gives every edge function `SUPABASE_URL` and the server key, read as the webhook reads it (`SUPABASE_SECRET_KEYS`, else `SUPABASE_SERVICE_ROLE_KEY`). The publishable key, for the calls made with the person's own token, is the `default` entry of `SUPABASE_PUBLISHABLE_KEYS`, else the legacy `SUPABASE_ANON_KEY`. Those two names could not be checked against Supabase's own documentation from here: look under Edge Functions, Secrets, before relying on the function. Nothing else is set.

**Deploying it.** JWT verification off: a browser's preflight carries no token, and the function asks Supabase Auth about the token itself. With the CLI, from the repository root: `supabase functions deploy delete-account --no-verify-jwt`. Through the Supabase MCP server or the dashboard: `delete-account/index.ts`, `delete-account/handler.ts`, `_shared/server.ts` and `_shared/http.ts`, with `verify_jwt` off. Apply `20261120000200` first: without it the function answers 500 `try_again`, and deletes nothing.

**Backups.** A deleted account is gone from the database at once. Copies in the server's backups are deleted when those backups expire, after the retention of the project's plan (Database, Backups, in Supabase's dashboard).

### A request through the contact form

Someone who cannot sign in asks through the contact form; minemuster.com/delete-account links to it as `/contact?about=delete-account`, which starts the message for them. The owner handles it in the SQL editor and Supabase's dashboard, all within 30 days of the person's confirmation:

1. Reply from MineMuster's own address to the email given, without saying whether it has an account: "If a MineMuster account uses this email, reply to confirm and we delete it."
2. On a reply from that same address, find the account under Authentication, Users, and ask whether it is a company's last supervisor: `select public.is_last_supervisor('<user id>');`. If it is, write to the company to make someone else a supervisor or close the company, and wait for that.
3. Otherwise delete the user there (Delete user), which is a hard delete, the same as the function's.
4. Reply "Your MineMuster account is deleted." Then mark the message handled and delete it: `update public.contact_requests set handled = true where id = '<id>';` and `delete from public.contact_requests where id = '<id>';`.

Someone who no longer has that email asks a supervisor at their company to take them off the roster, and says so in the form; the owner checks with the company before deleting anything. A crew member has no email on the server at all: they delete their account in the app with their passcode (which still works after they are taken off the roster), or ask a supervisor to delete the sign-in on the dashboard's Roster page, and the owner has nothing to do.

## Applying the migrations to a Supabase project

Being done now for the MineMuster project. Never from a test:

1. Apply the files in `migrations/`, in order, once each, to a project on PostgreSQL 15 or newer. New Supabase projects are; `select version();` in the SQL editor shows what an older one runs. The migrations expect what Supabase already provides (the `auth` schema, `auth.users` with its `deleted_at` and `banned_until` columns, `auth.uid()`, `auth.jwt()` and the roles), and they neither create nor change any of it. An extension already in `public` is left alone too. Do not apply anything from `tests/`.
   - With the [Supabase CLI](https://supabase.com/docs/guides/cli), from the repository root: `supabase link --project-ref <project-ref>`, then `supabase db push`. The CLI records which migrations have run, so a later `supabase db push` applies only new ones; `supabase migration list` shows where things stand. (`supabase init` first if the CLI asks for a `supabase/config.toml`.)
   - To try them on Supabase's local stack first: `supabase start`, then `supabase db reset`.
   - Without the CLI: paste each file into the dashboard's SQL editor, in order.
   - Before `20261120000100`: run `checks/shared_shapes.sql` first, in the SQL editor or with `psql -f`. It changes nothing that lasts: its two functions are copies of the migration's own (`office_changes.db.mjs` fails if they differ), made in the session's temporary schema. It lists every record of the settings, the roster, the fleet and the area sheets in a shape the migration refuses, and every unit whose status is better than the company's open maintenance requests on it. Like the migration, it checks only the name and the state of a company, so a company the phones cannot read for its pay schedule, mine ID or earning codes is not listed. Fix each on the dashboard, or decide with the owner, before applying the migration. Once it is applied, a phone passes over a record of the first list, and a change that leaves it in that shape is set aside (`malformed`); a unit of the second list is not saved again at a status better than its open requests (`open_request`).
2. Run the dashboard's Security Advisor. It may point out that the functions above are `security definer` and callable by signed-in users, `company_by_code` by any signed-in account, and `is_last_supervisor` and `step_down_everywhere` by the server key. That is on purpose: each one checks who is calling, and nothing else is callable. It may also point out `company_supervisor_guard` and `join_holds` as tables with row level security on and no policy: that is on purpose too, since only the functions use them.
3. Turn on the sign-in providers in Supabase Auth. The database needs nothing more: it reads the account from `auth.uid()`. If anonymous sign-ins are turned on, `join_company` and `create_company` refuse them (they read `is_anonymous` from `auth.jwt()`), so a throwaway account cannot claim rows or leave requests; still, leaving anonymous sign-ins off keeps that surface closed entirely.
4. Any server code that soft-deletes or bans accounts calls `step_down_everywhere(user_id)` first, and bans only once it has returned, as [A company always keeps a supervisor](#a-company-always-keeps-a-supervisor) says.
5. Keep PostgREST's `db-plan-enabled` off (see [What a count can tell](#what-a-count-can-tell)).
6. For billing (`20261117000500`): keep the webhook's signing secret in Vault as `stripe_webhook_secret`, deploy `functions/stripe-webhook` with JWT verification off, and point a Stripe webhook endpoint at it for the four events it uses, as [The webhook](#the-webhook) says. The Security Advisor may point out `stripe_events` and `contact_requests` as tables with row level security on and no policy, and `submit_contact_request` as callable by `anon`: on purpose, as above.
7. For deleting accounts (`20261120000200`): deploy `functions/delete-account`, with `_shared/server.ts` and `_shared/http.ts`, with JWT verification off, and check the names of its settings, as [Deleting an account](#deleting-an-account) says. It needs no secret of its own. The Security Advisor may point out `account_deletion_check` and `close_company` as `security definer` functions callable by signed-in users: on purpose; each answers for the caller alone.

8. For crew sign-in (`20261122000100`): deploy `functions/crew-auth`, with `_shared/server.ts` and `_shared/http.ts`, with JWT verification off, as [The crew-auth function](#the-crew-auth-function) says, and check that Supabase Auth keeps sessions with no time limit or inactivity timeout. ### Adding to it later

- One new file in `migrations/` per change, named `YYYYMMDDHHMMSS_what_it_does.sql`. Never edit a migration that has been applied; write a new one.
- Lock a new table in the file that makes it: `enable row level security`, `revoke all ... from public, anon, authenticated` and `revoke truncate ... from service_role`. Grant and add policies in the same migration, or in the next one.
- Turn a new table's planner statistics off in the file that makes it, before it holds data: `alter table ... alter column ... set statistics 0` for every column, as `20261116002200_no_planner_statistics.sql` does. A test checks every column of every table in `public`.
- Every new function gets `set search_path = pg_catalog, pg_temp` (pg_catalog first so unqualified type names resolve against it, the temporary schema last so a session cannot shadow a type or relation), fully qualified names, `revoke all on function ... from public, anon, authenticated, service_role`, and a grant to the roles that call it. Supabase grants EXECUTE on every new function in `public` to everyone unless the migration takes it back.
- PostgreSQL checks EXECUTE against the role doing the write, even for a function called from a check constraint or inside a trigger. So constraints use built-in functions only, and a trigger that calls a private helper is `security definer`.
- A trigger that checks a value checks it when that value is written (on insert, or when it changes), not on every update of the row, so a rule made stricter later never blocks an unrelated change to an older row, such as a foreign key clearing a claim.
- Never sweep a schema: name each object a migration alters, as `20261116001600_search_path_hardening.sql` names its functions. On a real project `public` already holds what these migrations must leave alone: an extension's functions (owned by the bootstrap superuser, since on Supabase `postgres` is not one), and the project's own procedures, aggregates and functions, such as a trigger on `auth.users` that finds its tables by the default `search_path`. A loop over the catalog is fine only over a list of names, as `20261116002200_no_planner_statistics.sql` loops over its tables.
- A row level security policy never calls a function on the row's own column. It compares the column with the caller's own companies, worked out once per statement: `company_id = any ((select public.member_company_ids())::uuid[])`, or `supervisor_company_ids()` for what only a supervisor may do. `row_reads.db.mjs` checks the plans.
- Keep the files plain ASCII: write a character such as a no-break space as a regular-expression escape (`\x00a0`). A test checks this.
- Add a test beside the others, and keep the names in it made up.
